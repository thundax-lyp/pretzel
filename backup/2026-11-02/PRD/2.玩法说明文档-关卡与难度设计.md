## 1. 文档目的与设计总纲

本文档定义游戏的关卡结构、题库机制与第二关难度分级算法，并**明确划分服务端与端侧（小游戏客户端）的职责边界**。核心设计原则：

- **第一关（教学关）纯端侧实现**：数据固定、卡牌和题库随机，不依赖网络，保证每次进入游戏都能秒开教学体验。
- **第二关（正式关）必须由服务端下发**：卡牌数量、叠放层数、卡牌排列与题目全部由服务端生成并下发，端侧只负责渲染与玩法逻辑，保证难度可控、可运营调参、可统计真实通过率。
- **难度是一个运营参数，不只是一个算法结果**：算法负责把第二关划分成低/中/高三档参数包络，运营后台负责决定"当前时段用哪一档"。

## 2. 基础规则回顾（名词定义）

以下规则沿用 PRD，本文档在此基础上细化。

| 名词 | 定义 |
|---|---|
| 卡牌 | 一张卡牌代表一种动物，具有两个属性：**眼睛数 E ∈ {2, 4}**、**腿数 L ∈ {0, 1, 2, 3, 4, 8}**。共 2×6 = **12 种卡牌类型** |
| 卡牌区 | 多层叠放的卡牌区域。卡牌按层堆叠，上层压住下层；**只有未被完全遮挡的卡牌可点击** |
| 卡槽 | 屏幕底部固定 **7 格**横向槽位。点击卡牌后按点击顺序移入空位 |
| 题目 | 一条形如"**{E}只眼睛{L}条腿**"的描述（如"两只眼睛四条腿"），附带所需张数 K（建议默认 **3 张**，由服务端随题目下发）。玩家将 K 张符合该组合的卡牌集入卡槽即完成该题并消除 |
| 消除 | 集齐一道题目的全部卡牌后，这些卡牌播放消除动画并移出游戏 |
| 胜利 | 本局全部题目完成，卡牌区与卡槽内不再存在属于题目的卡牌 |
| 失败 | 卡槽 7 格全部占满且不存在可消除组合。本游戏无复活 |
| 道具 | 三种：**移除**（将卡槽内所有卡牌移回卡牌区上方暂存区）、**撤回**（撤回最近一次入槽的卡牌）、**洗牌**（未消除卡牌位置随机重排）。每局每道具最多使用 2 次。**第一关禁止使用与获取道具** |

> ⚠️ 与 PRD 的差异需对齐：PRD 中"卡槽内集齐题目中腿的数量总和张动物卡牌即消除"。若按"张数=腿数总和"执行，则"四只眼睛八条腿"最多需 4 张，超过 7 格卡槽容量，规则不可满足。本文档按"**每题所需张数 K 由服务端下发，默认 3 张**"设计，请产品确认后统一修订 PRD。

## 3. 关卡设计

### 3.1 关卡总览

| 维度 | 第一关（教学关） | 第二关（正式关） |
|---|---|---|
| 出现时机 | **每次进入游戏都会出现**（每次开局必经） | 第一关通过后进入 |
| 数据来源 | **端侧本地生成**（题库随机内置） | **必须由服务端生成并下发** |
| 卡牌数量 | 固定 **30 张** | 随机 **80–120 张** |
| 卡牌分布 | 全部集中在**卡牌中心区域**排列 | 全屏区域排列，分布可由服务端下发 |
| 最大叠放层数 | **3 层** | 最高 **12 层**（具体层数由服务器下发） |
| 题目难度 | 简单概念题 | 按运营配置该时段的低/中/高三档生成 |
| 道具 | **禁止使用、禁止获取**（道具按钮置灰并提示"体验关不可用"） | 正常使用 |
| 胜利后 | 直接进入第二关（无胜利弹窗，展示一句“难度飙升”引导文案） | 弹出胜利对话框，走正常排行分数提报流程 |

### 3.2 第一关 · 教学关

**定位**：让玩家在 30 秒内理解"看题目 → 找对应卡牌 → 集齐消除"的核心循环。每次进入游戏都出现，同时承担热身作用。

**规则明细**：

1. **卡牌规模**：固定 30 张，全部由端侧按内置规则随机生成。
2. **布局规则**：所有卡牌集中在卡牌中心区域排列，最多叠放 **3 层**。端侧内置 2–3 套固定布局模板（如 10×3 中心矩阵），随机选用一套，避免每次完全一样。
3. **题库**：端侧内置简单概念题库，题目均为"低稀缺度"组合，例如：
   - 两只眼睛四条腿
   - 两只眼睛两条腿
   - 四只眼睛四条腿
   - 四只眼睛八条腿
4. **题目数量**：建议 最多10 道题（每题 3 张 × 10 题 + 少量冗余卡 = 30 张），保证教学关通过率接近 100%。
5. **道具限制**：道具按钮全程置灰，无法点击。
6. **引导提示**：不需要引导。

**端侧实现要求**：

- 教学关题库、布局模板、生成逻辑全部打包进代码包，**不发任何网络请求**，弱网/离线均可进入。
- 生成逻辑必须保证 30 张卡中每张卡都属于某道题的目标集合（可解性由本地规则直接保证）。

### 3.3 第二关 · 正式关

**定位**：真正的挑战关卡，难度、通过率、变现（道具消耗）都在这一关发生。

**规则明细**：

1. **卡牌数量**：每局随机 **80–120 张**。
2. **叠放层数**：最高 **12 层**；本局具体层数由**服务器下发**，端侧不得自行决定或修改。
3. **排列规则**：端侧与服务器结合生成——服务端下发给定本局的**完整卡牌排列数据**（见 6.2 节字段），端侧按数据还原布局并渲染。端侧只做合法性校验（总数、层数上限、坐标范围），不做任何二次随机。
4. **题目**：由服务端按第 4 章难度算法生成，随开局数据一并下发。
5. **胜负**：规则同第 2 章；结局（胜/败、用时、道具使用）由端侧上报服务端，用于通过率统计与难度调参。

### 3.4 开局交互时序（端 ↔ 服）

```
端侧                                    服务端
 │  ① POST /api/v1/level/start          │
 │ ───────────────────────────────────► │ 读取运营难度配置（当前时段档位）
 │                                      │ 按档位参数包络生成第二关：
 │                                      │   卡牌数N / 层数L / 卡牌排列 / 题目
 │  ② 返回 levelConfig（布局+题目+难度） │ 做可解性校验后落库（局快照）
 │ ◄─────────────────────────────────── │
 │ ③ 端侧校验数据合法性 → 渲染卡牌区      │
 │ ④ 玩家游玩（消除/道具/胜负）           │
 │ ⑤ POST /api/v1/report/batch 上报结局  │
 │ ───────────────────────────────────► │ 统计通过率 → 反哺运营调参
```

> 第二关的生成请求建议挂接现有 `POST /api/v1/match/start`（接口文档中已预留），或新增 `POST /api/v1/level/start`，以接口文档最终定稿为准。

## 4. 题库与难度设计

### 4.1 卡牌类型体系

卡牌由两个维度组合而成，共 12 种类型：

| 腿数 \ 眼睛数 | 两只眼睛（E=2） | 四只眼睛（E=4） |
|---|---|---|
| 0 条腿 | ✔ 占位卡（见 5.1） | ✔ |
| 1 条腿 | ✔ 奇数腿卡（见 5.2） | ✔ 奇数腿卡 |
| 2 条腿 | ✔ | ✔ |
| 3 条腿 | ✔ 奇数腿卡 | ✔ 奇数腿卡 |
| 4 条腿 | ✔ | ✔ |
| 6 条腿 | ✔ | ✔ |
| 8 条腿 | ✔ | ✔ |

**设计含义**：

- 偶数腿组合（0/2/4/6/8）是**常规题库素材**，玩家认知成本低（现实中常见：蛇 0 腿、母鸡 2 腿、猫狗 4 腿、蜘蛛螃蟹 8 腿）。
- 奇数腿组合（1/3）**不进入常规题目**，仅作为干扰卡存在（见 5.2），是难度与通过率的调节阀。

### 4.2 题库结构与题目难度系数

题库中每道题目由三元组描述：`题目 = (眼睛数 E, 腿数 L, 所需张数 K)`，另带一个**基础难度系数 r ∈ [0, 1]**。

**r 的取值由目标组合在牌堆中的稀缺度决定**：一种组合的卡牌越少、埋藏越深，找齐越难，系数越高。基础系数参考表（服务端可配置）：

| 题目示例 | 基础系数 r | 说明 |
|---|---|---|
| 两只眼睛两条腿 | 0.2 | 最常见组合，素材充足 |
| 两只眼睛四条腿 | 0.3 | 常见 |
| 四只眼睛四条腿 | 0.4 | 四眼动物较少 |
| 两只眼睛零条腿 | 0.5 | 占位卡专属题，卡牌数量大但专属题少 |
| 四只眼睛两条腿 | 0.5 | |
| 两只眼睛八条腿 | 0.7 | 八腿动物稀缺 |
| 四只眼睛八条腿 | 0.8 | 双稀缺维度 |
| 两只眼睛一条腿 / 三条腿 | 1.0 | **彩蛋题，仅彩蛋局出现**（见 5.2） |

**出题规则**：题库根据**本局卡牌数量与卡牌分布**生成相应难度系数的题目——服务端先确定卡牌分布，再从题库中挑选系数匹配、且目标卡牌数量恰好满足 `K × 题数 ≈ 该组合卡牌数` 的题目。生成时必须满足：

1. 每张偶数腿卡牌都属于恰好一道题的目标集合（保证可全部消除）。
2. 所有题目所需卡牌总数 ≤ 本局总卡牌数（奇数腿卡为差额部分）。
3. 同一局内不出现重复题目。

### 4.3 第二关三档难度划分算法

第二关划分为**低难度、中难度、高难度**三个等级。划分方式采用"**参数包络 + 难度分校验**"两步法：

**第一步：三档参数包络（生成时采样空间）**

| 参数 | 低难度 | 中难度 | 高难度 |
|---|---|---|---|
| 卡牌总数 N | 80–90 张 | 90–105 张 | 105–120 张 |
| 最大层数 L | 4–6 层 | 6–9 层 | 9–12 层 |
| 无腿卡占比 p₀ | ≤ 8% | 8%–14% | 14%–20% |
| 奇数腿卡占比 p_odd | 0–3% | 3%–8% | 8%–15% |
| 题目系数区间 | 全部 r ≤ 0.4 | r ∈ [0.4, 0.7] 为主 | r ∈ [0.7, 1.0] 占比 ≥ 50% |
| 题目数量 | 8–10 道 | 10–13 道 | 13–16 道 |

**第二步：难度分校验（生成结果回归验证）**

服务端对每次生成的本局配置计算难度分：

```
S = 0.30 × (N − 80) / 40        ← 体量因子：卡牌越多越难
  + 0.30 × (L − 3) / 9          ← 层数因子：叠得越深越难
  + 0.15 × p₀                   ← 占位因子：无腿卡越多越难
  + 0.15 × p_odd                ← 干扰因子：奇数腿卡越多越难
  + 0.10 × r̄                   ← 题目因子：所选题目平均系数
```

判定：`S < 0.40` 为低难度，`0.40 ≤ S < 0.70` 为中难度，`S ≥ 0.70` 为高难度。

**闭环规则**：服务端在目标档位的包络内随机采样生成一局配置 → 计算难度分 S → 若 S 落在目标档位区间则通过，否则重新采样（最多重试 3 次，仍未命中则取最接近的一版）。这保证"运营选的档位"与"玩家实际体验的难度"一致。

**第三步（可选进阶）：通过率反馈修正**

上线后以真实通过率为准绳校准权重：目标通过率参考值 低 85% / 中 50% / 高 20%。若某档位实测通过率连续 3 天偏离目标 ±10 个百分点，运营在后台微调 p₀、p_odd 上限或题目系数区间即可，无需改代码。

### 4.4 服务端生成流程（汇总）

```
读取运营难度档位配置（当前时段）
   ↓
在对应档位参数包络内采样：N、L、各腿型数量、题目集合
   ↓
生成卡牌排列（层号 + 区域坐标），奇数腿卡优先压在深层
   ↓
可解性校验：模拟求解（7 格卡槽 + 3 道具），确认存在通关路径
   ↓
难度分 S 校验，落在目标档位区间内
   ↓
落库局快照（局 ID、配置、难度档位）→ 下发端侧
```

## 5. 特殊卡牌设计意图

### 5.1 无腿卡（0 条腿）—— 占位卡

**为什么存在**：无腿卡的设计目的就是**占卡槽**。它们数量多、自身消除路径单一（只能通过"X只眼睛零条腿"这类专属题目消除），会持续挤占 7 格卡槽空间。

**玩家策略影响**：玩家必须在尽可能早的时候把无腿卡消除掉——先把"零条腿"题目做掉，给后续卡牌腾出卡槽空间；拖到后期无腿卡塞满卡槽即失败。这让"做题顺序"成为核心策略点，而不是无脑找相同的卡。

**生成规则**：每局固定包含 1–2 道"零条腿"专属题目；无腿卡占比按难度档位递增（见 4.3 表）。

### 5.2 奇数腿卡（1 条腿 / 3 条腿）—— 通过率调控 + 彩蛋

**通过率调控（主要作用）**：常规题库中不存在奇数腿题目，奇数腿卡**无法通过做题消除**，玩家只能点击它们入槽（为了取其下方的卡）再消耗**移除道具**将其请出卡槽。它们是纯粹的卡槽毒瘤：

- 奇数腿卡占比 p_odd 越高，道具消耗越多、失败概率越大 → 服务端通过调节 p_odd 精准控制通过率（IAA 变现随之提升）。
- 生成规则：奇数腿卡优先埋放在深层（上层），最大化"不得不取"的次数；其数量上限受"道具总移除容量"约束（每局移除道具最多 2 次 × 每次最多清空 7 格），保证关卡在合理使用道具下可通关。

**彩蛋（辅助作用）**：极小概率（建议 < 5%，由服务端控制）本局会下发一道**隐藏彩蛋题**，如"两只眼睛一条腿"或"四只眼睛三条腿"，该局的奇数腿卡即成为可消除的目标卡。玩家在毫无预期时发现"原来这条独腿怪也能消"，触发限定隐藏动画与隐藏图鉴。彩蛋局不改变当局难度档位，仅改变奇数腿卡的性质。

## 6. 职责划分：服务端做什么，端侧做什么

### 6.1 边界总原则

1. **第一关的一切归端侧，第二关的一切归服务端**——端侧不得为第二关做任何本地生成或本地兜底随机。
2. 服务端是难度的唯一权威：层数、卡牌分布、题目、难度档位均以下发数据为准，端侧仅校验格式合法性。
3. 端侧是体验的唯一权威：拾取判定、遮挡关系、消除动画、道具效果全在端侧本地实现，服务端不逐步校验操作过程（MVP 阶段信任端侧上报，接口文档约定同）。

### 6.2 服务端职责

| # | 职责 | 说明 |
|---|---|---|
| S1 | 存储并读取运营难度配置 | 提供"当前时段使用的难度档位"配置的存取（见第 7 章），开局时读取生效 |
| S2 | 生成第二关配置 | 按档位包络采样卡牌总数 N（80–120）、层数 L（≤12）、各类型卡牌数量、题目集合与所需张数 K |
| S3 | 生成卡牌排列规则 | 为每张卡分配层号与区域坐标（layer/row/col），做深层压置策略（奇数腿、稀缺卡靠下） |
| S4 | 可解性与难度分校验 | 模拟求解确认可通关；计算难度分 S 确认落在目标档位 |
| S5 | 下发开局数据 | 返回 `levelConfig`：`{ level_id, difficulty, card_total, max_layer, cards:[{card_id, type, layer, x, y}], questions:[{E, L, K, desc}] }` |
| S6 | 结局接收与统计 | 接收端侧上报的胜/败、用时、道具使用，按难度档位统计真实通过率 |
| S7 | 局快照落库 | 保存每局生成配置，供复盘、客诉核查与后续对局校验扩展 |

### 6.3 端侧职责

| # | 职责 | 说明 |
|---|---|---|
| C1 | 第一关全量本地实现 | 内置 30 张卡的布局模板与简单题库（2眼2腿 / 2眼4腿 / 4眼4腿 / 4眼8腿 等），中心区域排列、最多 3 层；不发网络请求 |
| C2 | 教学关道具封锁 | 第一关道具按钮置灰、获取入口隐藏 |
| C3 | 请求并校验第二关数据 | 调用开局接口，校验 card_total ∈ [80,120]、max_layer ≤ 12、cards 与 questions 数量一致；校验失败按第 8 章降级 |
| C4 | 还原卡牌布局 | 严格按服务端下发的 layer/x/y 渲染叠放，不做二次随机、不改动顺序 |
| C5 | 玩法逻辑本地实现 | 遮挡判定与点击拾取、入槽动画、题目集齐消除、胜负判定、三种道具效果、计时 |
| C6 | 结局上报 | 上报对局结果事件（沿用 `/report/batch` 事件通道），携带难度档位与局 ID |
| C7 | 引导与提示 | 教学关引导动画；第二关题目区常驻展示当前题目进度 |

### 6.4 禁止事项（双向约束）

- ❌ 端侧不得在第二关本地生成或修改卡牌数量、层数、排列、题目。
- ❌ 端侧不得在教学关启用任何道具。
- ❌ 服务端不参与游玩过程的逐步校验，不感知每次点击（MVP 约定）。

## 7. 运营后台难度配置

**配置模型**：运营后台（admin-api）维护一张难度档位配置表，核心字段：

| 字段 | 说明 | 示例 |
|---|---|---|
| difficulty | 档位：LOW / MID / HIGH | MID |
| time_rule | 生效时段规则（支持按星期 × 小时段） | 工作日 12:00–14:00、19:00–23:00 = HIGH；其余 = MID；周末全天 = LOW |
| p0_max / p_odd_max | 占位卡、奇数腿卡占比上限微调 | p0_max=0.14 |
| question_r_range | 题目系数区间微调 | [0.4, 0.7] |
| egg_rate | 彩蛋局概率 | 0.05 |
| status | 启用状态 | 启用 |

**典型运营策略**（示例，供参考）：

- 晚间高峰（19:00–23:00）玩家基数最大 → 配高难度，压通过率、拉道具消耗与分享。
- 周末全天 → 配低难度，拉活跃与通关成就感。
- 版本大推期间整体下调一档，保护新增留存。

**生效链路**：后台保存配置 → admin-api 落库 → game-api 开局时读取最新配置并按其生成第二关 → 端侧在下发数据中拿到 `difficulty` 字段用于展示与上报。配置实时生效（下一局即用新档位），端侧无需发版。

## 8. 异常与降级

| 场景 | 处理方式 |
|---|---|
| 第二关开局请求失败 / 超时 | 端侧展示"网络开小差"重试弹窗，自动重试 2 次；仍失败则返回首页。**禁止本地兜底生成第二关** |
| 下发数据校验失败（字段缺失、数量越界） | 同上按请求失败处理，并上报异常事件（携带 trace_id） |
| 教学关 | 纯本地，无网络依赖，不受任何异常影响 |
| 服务端生成重试 3 次仍不落档位区间 | 取难度分最接近目标档位的一版下发，并在局快照中标记 `fallback=true` 供事后观察 |
| 彩蛋局 | 由服务端在生成时掷骰决定并体现在题目中，端侧无感知差异，正常渲染即可 |

## 9. 验证指标

上线后以以下指标验证难度设计是否达成（按难度档位拆分统计）：

| 指标 | 目标参考 |
|---|---|
| 教学关通过率 | ≥ 100% |
| 第二关通过率（按档位） | 低 ≈ 85% / 中 ≈ 50% / 高 ≈ 20% |
| 平均对局时长 | 低 3–5 分钟 / 中 5–8 分钟 / 高 8 分钟以上 |
| 道具使用率 | 随档位递增；高难度局道具参与率 ≥ 60% |
| 失败后分享/看视频率 | 反映"差一点就过"的难度手感，目标 ≥ 25% |
| 彩蛋局触发率与发现率 | 触发率 ≈ 配置值；发现率（完成彩蛋题）≥ 80% |
