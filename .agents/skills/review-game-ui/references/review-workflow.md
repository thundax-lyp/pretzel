# 游戏 UI 与 UE 审核流程

本参考文件维护整体观察、对象拆分、证据要求与复核。检测点列表由 review-checks.md 维护；各点的判据和方法组分别在 `checks/<category>.md#<point-anchor>`，共享操作细则在 `methods/<topic>.md#<method-anchor>`。review-queue.md 负责建队列，parallel-review.md 负责分派，result-contract.md 统一单项返回，report-output.md 定义统一意见与逐截图交付。

阅读顺序：使用方式与覆盖要求 → 明确审核上下文 → 第一步整体观察 → 第二步拆分对象 → 第三步逐项检查与记录 → 判据、证据与适用条件 → 跨对象复核 → 第四步合并意见 → 第五步整体复核 → 完成边界。进行检查前先读方法与证据要求，再按对象类别选择细则。

审核顺序为：明确类型与目标体验 → 整体看效果 → 按职责拆分对象并分类 → 检测点入队并执行 → 单项报告 → 统一修改意见 → 逐截图修改单 → 回到整体复核。先形成整屏判断，再用分类检查定位原因；局部检查通过不能代替整体审美判断。

本流程适用于游戏界面设计稿、截图、可操作原型和实际运行画面。设计原则定义通用取舍，修改方案定义具体产品的风格、尺寸与行为；审核结论说明观察到的问题及其证据。

各阶段采用提问式思考，由审核者结合画面与行为作答。问题用于展开观察与判断，不是逐条向用户索要答案。确实缺少会影响判断的目标或上下文时，再集中澄清。

## 使用方式与覆盖要求

### 基础覆盖与场景选用

每次审核都覆盖实际材料中的整体效果、主要区域、核心游戏对象、文字图形、主要操作、对象间关系，以及已经出现的状态。不能因为清单较长，就只选择容易通过的条目。

根据当前能力选用导航、列表、弹层、引导、奖励、道具、商业化、复杂输入等问题。不存在的能力标为不适用，不要求增加功能；已有能力的失败、边界和恢复状态不能因缺少截图就标为不适用，应列为待验证。

本流程是可扩展的检查框架。完成已选问题不等于证明所有设计都正确；发现无法归入现有类别的问题时，保留观察并补充分类，不删除问题以适应表格。

### 覆盖总表

| 审核领域         | 基础关注                               | 按实际场景扩展                         |
| ---------------- | -------------------------------------- | -------------------------------------- |
| 整体审美与类型   | 情绪、主题、构图、比例、趣味、风格     | 宣传展示与实际游玩目标差异             |
| 区域与布局       | 归属、主次、对齐、间距、留白、视觉顺序 | 滚动、固定区域、动态重排               |
| 色彩与材质       | 和谐、明暗、强调、形体、细节一致       | 纹理、透明叠加、主题或显示模式变化     |
| 背景与场景       | 氛围、前景分离、空间感、裁切           | 环境运动、视差、场景切换               |
| 游戏与收集对象   | 身份、属性、轮廓、尺度、关系           | 叠放、锁定、选择、特殊标记、数量变化   |
| 文字与图标       | 气质、字号、字重、排版、颜色、含义     | 长内容、多语言、动态数值、字体替代     |
| 操作与导航       | 用途、优先级、命中、反馈、返回         | 手势、拖动、长按、键鼠或手柄导航       |
| 容器与内容浏览   | 内容组织、主体比例、可达性             | 列表、网格、分页、筛选、排序           |
| 临时内容与状态   | 层级、打断、状态含义、下一步           | 弹层、通知、错误、风险确认             |
| 动态与多感官反馈 | 动作含义、强度、时机、遮挡             | 转场、声音、触觉、同时触发与中断       |
| 学习与阶段流程   | 目标理解、操作与结果对应               | 新手引导、提示、重复游玩、阶段切换     |
| 成果与资源       | 真实变化、成本、去向                   | 领奖、排名、道具、广告或付费           |
| 边界与恢复       | 已出现状态的完整性与一致性             | 慢网、离线、未知结果、暂停、恢复       |
| 适配与成品质量   | 实际尺度、清晰度、边界、输入环境       | 屏幕变化、资源失败、文字缩放、减少动效 |
| 跨对象与跨页面   | 层级竞争、语义、风格、连续性           | 多状态叠加、多个入口共享同一事实       |

审核前对本次范围建立覆盖表：列出页面、状态、主要对象、适用规则及材料。审核后记录已检查、不适用或待验证及其原因，不能把未看到当作没有问题。

### 从原则提取检测点与方法

原则 → 检测点列表 → 截图/对象/状态上的检测队列 → 本点方法组 → 单项报告 → 统一意见 → 逐截图修改单 → 复核记录，构成完整链路。原则定义设计意图，细则定义可检查的条件，记录才说明某个版本的实际结果。

提取时遵守以下要求：

1. 每条原则有稳定编号，每个检测点归属一个主原则；相关原则可以辅助解释，但不重复建立同一检查。每条原则至少有一个检测点，不能只有口号而无检查入口。
2. 每个检测点只回答一个可以独立作出结论的问题。字号可读与字号层级、字色和谐与文字对比应分别检查；其中一项通过不能代表另一项通过。
3. 检测点写清原则来源、提问、判据、最低证据及所需方法；检测方法单独写清适用输入、操作步骤、产出和限制。对象与情境由当次审核展开，通用细则不绑定项目页面或具体数值。
4. 状态或内容改变可能使结论改变时，建立不同记录。例如正常文字和长名称、可用和处理中分别检查，不用默认态覆盖全部状态。
5. 能测量的项目依据有效约定记录实测值；审美项目记录可观察关系和判断理由。两者都需要证据，但不能用数值合格替代和谐、有趣或有个性的判断。
6. 新发现超出细则时先保留观察，再检查是否漏提取了已有原则，或需要补充原则。修改原则时同步检查对应细则，不把某次修图的具体参数提升为通用原则。

原则与细则的编号对应只证明有检查入口，不自动证明细则充分，也不证明设计通过。维护时仍需审视每条原则的重要条件是否被拆出，是否存在一个检查内可能产生不同结论的多个问题。

## 明确审核上下文

先说明游戏类型、目标玩家、当前任务、期望情绪、视觉方向、输入方式和观看环境。区分实际游玩、辅助功能与宣传展示，不把不同目标的画面放在同一审美尺度上比较。

需要回答：

- 玩家此刻在观察、比较、操作、浏览、学习还是等待？哪些信息直接影响下一步决定？
- 画面希望带来什么感受？哪些内容应该最先被注意，哪些只需要在需要时找到？
- 哪些挑战来自玩法，哪些负担只是排版、理解或操作障碍？
- 哪些视觉要求已经明确，哪些属于待讨论的方向？参考画面是在提供风格，还是已经约定具体内容？
- 材料对应哪个版本、页面与状态？设计稿、旧截图和当前运行画面是否被混在一起？
- 实际观看尺度、设备系统覆盖和输入条件是否已知？哪些判断目前没有足够材料？

不必为了补齐表格而猜测玩家画像或设计目标。已知条件写清，重要未知保留；能独立开展的画面检查继续进行。

## 第一步 整体看效果

先以实际观看尺度观察完整画面，不立即放大单个控件或先查尺寸。对照必要的相邻页面与连续操作，先问整体感受，再定位原因。

| 观察维度     | 提问                                                                             |
| ------------ | -------------------------------------------------------------------------------- |
| 主题与情绪   | 画面给人什么感受？这种感受适合当前活动吗？角色、环境与界面是否在表达同一种性格？ |
| 吸引力与个性 | 有让人愿意停留、探索或操作的内容吗？记忆点来自主题，还是只有通用装饰？           |
| 构图与视线   | 第一眼看到了什么？它应该是焦点吗？接下来能自然找到主体、信息与行动入口吗？       |
| 比例与疏密   | 主体、容器、文字与控件的体量协调吗？哪里拥挤、哪里空？这些变化在衬托什么？       |
| 色彩与明暗   | 大色块和谐吗？明暗是否组织了前后关系？强调色是否集中在真正重要的地方？           |
| 形体与材质   | 轮廓、光照、厚度、字体和质感相互呼应吗？有没有明显像来自其他作品的部分？         |
| 动静与节奏   | 哪些运动吸引注意？这种吸引有必要吗？日常、关键事件和等待是否有不同节奏？         |
| 完整感       | 画面是否有明确设计意图？少量内容、默认状态和繁忙状态都像完整作品吗？             |
| 体验方向     | 当前画面是在帮助观察、操作或享受成果吗？它是否把玩家推向了与任务无关的活动？     |

整体记录包含“保留什么、主要失衡是什么、目标效果是什么”。审美判断要指出可观察关系。例如“大面积重边框占据重心，主要对象被压缩”比“太土”更可讨论；指出关系不意味着美感只由尺寸计算决定。

缩略图、灰度、放大细节或遮去装饰可帮助定位问题，但只能作为辅助观察，不能替代正常尺度、正常颜色下的最终效果。整体问题尚未归因时保留观察，不为了套分类编造原因。

视觉方向明显不符时先确定构图、主体比例或风格调整，再安排依赖它的局部打磨。操作正确性等必要问题可以同步处理，不因美术方向待定而遗漏。

## 第二步 按职责拆分审核对象

按“整屏 → 功能区域 → 复合对象 → 必要子元素”拆分。功能区域由玩家在这里完成的任务确定，不按源码文件、节点数量或贴图张数划分。

### 对象记录

每个对象记录以下内容，规模较小时可以合并成简短表格：

| 内容           | 用途                                               |
| -------------- | -------------------------------------------------- |
| 所属页面与区域 | 明确它处于哪段流程、与哪些内容同屏                 |
| 对象编号       | 在同次审核中唯一，关系对象同时列出参与者编号       |
| 实际职责       | 区分内容、操作、状态、承托和装饰                   |
| 视觉层级       | 说明主内容、主要操作、辅助信息或环境装饰           |
| 对象类别       | 选择适用的分类问题，不由形状直接推断职责           |
| 状态与变化     | 列出已出现及需要验证的选择、禁用、等待、异常等状态 |
| 关联对象       | 指出对应文字、图标、数值、底板和受影响区域         |
| 可用材料       | 标明可观察画面、原型、运行记录或实现位置           |

### 对象类别

| 类别               | 包含内容                                     |
| ------------------ | -------------------------------------------- |
| 环境背景与场景装饰 | 远景、地面、氛围图形、非交互装饰             |
| 内容承托与分组     | 面板、底板、边框、标签、列表容器             |
| 游戏与收集对象     | 棋子、卡牌、角色、道具、收集成果             |
| 文字与信息图形     | 标题、正文、数值、单位、图标、状态与进度标记 |
| 操作与导航         | 按钮、分页、切换、滑杆、手势及其他输入入口   |
| 临时与阶段内容     | 提示、详情、等待、结果、异常、教学与确认     |
| 动态与多感官反馈   | 位移、粒子、转场、声音、震动                 |

对象类别与规则类别分开：按钮是对象，色彩、文字、材质、交互和反馈是它适用的规则；构图和配色也可能涉及多个对象。同一对象可以适用多类规则，但不能被复制成几个互不关联的审核条目。

### 拆分深度

文字先按职责建立对象：品牌名、情绪/阶段大标题、固定主要行动、功能标题、规则/说明、数值/单位。品牌与展示标题独立编号；同一个按钮的固定名称与可变数量分别说明。不同职责需要不同选型或判断时分别入队，不用“整页文字协调”统一收掉。普通功能标题以快速定位为主，数值和正文以稳定清楚为主；固定大品牌字和情绪字优先评估定制美术表达。

- 复合对象先看完整效果，再拆必要子元素。例如先看道具按钮的用途和体量，再看底板、图标、名称、数量与状态。
- 同类重复对象可以按组审核，但要覆盖正常、拥挤、边界与特殊状态，不能只选最好看的一项。
- 只有当子元素具有独立职责、影响关系或修改方向时才继续拆，避免为每个阴影和描边建立没有必要的独立条目。
- 先记录区域间关系，再检查对象细节，防止把整体比例问题误判为每个对象都需要放大。
- 一个规则涉及多对象时记录为关系问题，例如目标与已选值的对应、按钮与说明的距离，而不是强行归入某个素材。
- 不存在的对象标为不适用；缺少其实际状态的材料标为待验证，二者不能混用。

## 第三步 提问并逐项审核

每个对象先问“它承担什么职责？”，再问“表现是否合适、与周围是否协调？”，最后检查状态与操作。不要一开始就假设字号必须更大、颜色必须更亮或特效必须更多。

每项同时考虑审美、信息、操作与情境。静态材料先检查可观察部分；动态、命中、请求和恢复行为使用原型或运行证据验证。代码可以定位来源、核对消费链路和时序，不能用“代码存在该状态”代替看到实际效果。

### 作答要求

展示文字的审美判断回答字形个性、轮廓与节奏、厚度/材质/光影、趣味细节及品牌记忆，并比较文字与角色、场景的完成度。区分基础风格相容、文字美术表达充分与实际可读，这些结论不能互相代替。无需等到遮挡、错位或运行失败才提出有画面关系依据的审美调整；缺少真机、输入或动态证据只限制对应判断。没有修改后方案时明确所提为设计方向，不能宣称任何装饰字体必然更好。

作答包含**判断、理由、处理方向**：

- 判断使用通过、需调整、待验证或不适用；尚未执行时保留未检。
- 理由说明所见的画面关系、行为结果或仍缺失的证据。
- 处理方向说明保留什么、改变什么，或补看哪种材料；方向不能超出当前能力与有效约定。

不只填写“是／否”，也不把每个问题都变成修改任务。逐项记录保留，最终报告再按共同根因汇总；不按回答条数衡量审核质量。

例如回答“这个字号合适吗？”：“需要调整。辅助说明与主标题体量接近，削弱了标题层级；保持可读性的同时降低说明的视觉重量，再放回整屏比较。”没有实际尺度材料时，应写明阅读尺寸待验证，不能猜测已经通过。

### 按检测点建队列并逐项执行

1. parent 完成整体观察与对象拆分后，从 [检测点列表](review-checks.md) 选出各图、各对象与状态的适用点，按 [队列规则](review-queue.md) 形成 QUEUE.json。已有能力缺材料的点仍入队，写清待验。
2. 每项直接读取自己的 `checks/<category>.md#<point-anchor>`，取得判据、最低证据与整组方法；同一 owner 完成该点所有选中方法，不把一个点拆散到几个方法报告。
3. 独立项可按 [并行协议](parallel-review.md) 批量交给 subagent，或由 parent 串行执行。一个 subagent 可处理多个项，每项分别返回。
4. 返回只使用 [统一单项契约](result-contract.md) 的 JSON 字段和枚举，并从其展开单项 Markdown。方法执行、点结论与覆盖状态分开；不可用的必要方法也有明确未执行记录。
5. parent 核对材料、revision、方法覆盖及证据，接收或要求补验，再按共同根因形成统一意见。
6. 统一意见形成后按 [报告交付](report-output.md) 为每张输入截图写本图改法；不同状态分别说明，不以一条全局意见覆盖所有页面。

### 作答与状态

继续用提问展开观察，并记录判断、理由和处理方向；实际返回值以 result-contract.md 的英文枚举为准。人读报告显示通过、需调整、待验证、不适用，以及独立的覆盖状态。队列仍未执行或未接收的项保留在队列状态中，不伪装成已有检测结论。

例如同一字号点需要实际尺度阅读与几何测量：阅读缺证、测量仅完成部分时，分别保存 not_run/partial，该点为 pending/incomplete。若已见具体偏离，可以 adjust/incomplete，仍保留其余方法缺口；这不是提前关闭检测点。

同一截图的字号层级、字色和谐、实际背景阅读等是不同点，分别入队和作答。共享证据可以引用，点结论不能直接复制；修改后复查原点、方法和受影响的相邻项。

## 判据、证据与适用条件

review-checks.md 是检测点列表入口，每个 `checks/<category>.md#<point-anchor>` 保存自己的提问、判据与方法组，直接链接所需 `methods/<topic>.md#<method-anchor>`。编号的前半部分对应 GAME-UI-UE-PRINCIPLES.md 中的原则，后缀区分独立检查，例如 TXT-05.1 检查字色和谐，TXT-05.2 检查变化背景下的阅读。表中“通过判据”说明什么观察支持通过，不预先宣告当前设计已通过。

整体审美 VIS 与交互总原则 CORE 在第一步先检查；分类后为区域、复合对象及必要子元素逐项展开其余适用条目。跨对象规则以关系为对象，最后复查 VIS 与 CORE。不能因为字体、颜色等局部条目均通过，就推导整屏通过。

### 证据代号与适用条件

| 代号 | 最低材料要求                                         | 判断边界                                                       |
| ---- | ---------------------------------------------------- | -------------------------------------------------------------- |
| 图   | 对应版本、状态与正常显示尺度的完整画面，必要时附局部 | 放大图只能补看细节；需注明实际尺寸是否有证据                   |
| 动   | 覆盖事件前、过程中、结束及连续触发的录屏或现场观察   | 单帧不能证明节奏、遮挡持续与中断表现                           |
| 操   | 在目标输入环境中实际执行，并记录条件、动作与结果     | 可操作原型只证明原型范围；设备、版本和边界须注明               |
| 实   | 当前有效规则或契约，加对应状态的事实记录             | 涉及消费、发奖等实际结果时须有其权威状态，只有文案或源码不够   |
| 资   | 最终资源及其加载、缩放或替代情况                     | 资源本身清楚不等于合成后的画面清楚                             |
| 声   | 可听的实际播放及其连续过程，必要时对照录屏           | 无声录屏不能证明音色、混音或听觉连续性                         |
| 理   | 目标玩家或相应代表者的实际理解观察                   | 记录任务、参与条件、解释与困难；审核者自己会操作不证明玩家理解 |

阅读与辨认类任务中的“操”指在已确认的目标显示尺度与观看条件下实际完成阅读或辨认，不要求额外点击。比例明确的静态材料可以支持测量，但仍需记录实际显示与阅读条件；工具放大预览不能证明目标尺度可读。

“+”表示材料均需满足，可由同一次运行同时取得。表中证据是支持通过所需的最低类型，不是所有边界状态已覆盖的证明。证据不足以判断时标为待验证；已足够证明具体偏离时标为需调整，其他缺证状态另列记录。

“动态时加动”表示存在相应变化时补充动态材料，纯静态对象仍需检查其最终合成画面，不能整项标为不适用。

各领域只用于实际存在的对象与能力。声音、触觉、教学、排名、道具、广告、付费、特殊手势、多语言、辅助选项等不存在时记录不适用及原因；存在但未展示的状态列为待验证。屏幕、语言、输入与玩家条件以已约定支持范围选取，不由清单新增能力。

通过判据中的“适合”“协调”“合理”需要基于已记录的任务、情绪和风格方向说明具体关系。尺寸、对比、响应和性能等有项目指标时填写指标、测量方式及实测值；未约定时如实给出观察和建议，不编造通用数字门槛。审美判断可复查其理由，不应伪装成自动检测所得的客观结论。

## 跨对象与跨页面复核

逐项检查后单独检查关系，不能把它们视为所有单项结论的自然总和。以下是关系选取提示，实际记录仍引用对应检测点编号，以多个关联对象作为检查对象：

- 同一事实在不同区域显示一致吗？目标、已选内容、库存与结果能互相解释吗？对应 STATE-05.1。
- 多个对象同时使用强调色、放大或动效时，重心是否仍然清楚？分别对应 VIS-02.1、COL-02.1、MOT-04.1。
- 名称、图标、数字和操作在空间上归属正确吗？是否会把邻近内容误认为一组？对应 LAY-03.1、TXT-06.1。
- 固定控件、弹层、消息和滚动内容同时出现时，是否遮挡或争抢输入？分别对应 LAY-07.1、ACT-03.2、MOD-03.2。
- 相邻页面的字体、图标、轮廓和材质像同一游戏吗？任务差异是否有适当表现？对应 FORM-05.1、NAV-07.1。
- 返回和状态切换保持了合理位置、选择与视觉连续性吗？分别对应 NAV-01.2、MOT-06.1。
- 某个改动修好了局部，却使其他内容显得更小、更弱或更拥挤了吗？重新执行 VIS-03.1、VIS-03.2、ACC-08.1。
- 多个问题是否来自同一个背景、容器或整体比例，而不是多个独立素材？

## 第四步 合并并表达修改意见

每条意见说明页面与状态、整体观察、涉及对象、适用原则、可见后果、修改方向及复核方式。先区分结论性质：

| 结论           | 含义                                                   |
| -------------- | ------------------------------------------------------ |
| 审美调整       | 在既定类型与风格目标下，比例、构图、色彩等关系需要改善 |
| 规则或行为问题 | 具体内容、状态或操作不符合有效约定，已有可核对证据     |
| 待验证         | 观察成立但原因未确认，或缺少运行、动态及目标设备证据   |
| 可保留         | 当前表达支持目标体验，修改时保护其作用                 |

相同根因、相同触发情境和相同修改位置的问题合并，列出受影响对象；独立问题分别保留。整体构图问题不能被大量字号小问题掩盖，审美偏好也不能冒充已证明的行为缺陷。

修改优先级考虑整体视觉影响、任务影响和依赖关系。重大操作问题必须处理，风格与构图方向决定依赖它的打磨顺序；不要把所有类别打分后相加，也不用统一评分阈值替代适用性判断。

### 意见与单图动作的关系

统一意见使用 opinion_id 关联支持它的 item_id，说明共同根因、方向与取舍。每张实际受影响截图再拥有独立 action_id，写清该图位置、当前表现、目标、本图改法、保留项、依赖和复核。

结构化事实写 DECISIONS.json，具体字段与 Markdown 展开以 [报告交付](report-output.md) 为准。每张截图都有单页修改报告；没有已确认修改项时明确保留或待验证，不凑问题。统一意见合并不删除原单项报告，单页清单也不只写“按全局意见修改”。

## 第五步 回到整体复核

把修改放回同一整屏与连续流程，以相同尺度和可比较的状态复看：

- 原来的主要失衡改善了吗？主体与阅读顺序更清楚了吗？
- 配色、材质、形体与字体是否更协调？游戏的个性和趣味仍在吗？
- 留白、密度和比例是改善了，还是把内容变成另一种单调或拥挤？
- 局部放大、加底板或增加反馈是否产生新的视觉竞争？
- 正常、拥挤和边界状态都成立吗？动态过程会破坏静态构图吗？
- 与前后页面放在一起时，风格与操作节奏仍连续吗？
- 相应行为是否真的验证？缺少证据的项目是否仍保留为待验证？

再对照同类页面，检查共享视觉语言及场景应有的差异。需要动效的画面同时检查静止帧和运动过程，不选择粒子最少或信息最完整的一帧证明通过。

审核报告按“整体结论 → 统一修改意见 → 逐截图修改导航 → 单项检测与方法覆盖 → 整体复核结果或计划 → 未覆盖范围”组织。新效果尚未形成时，将整体复核列为后续验收，不能提前报告已改善。

## 判断材料与完成边界

| 材料                 | 可以支持的判断                         | 不能单独替代                                 |
| -------------------- | -------------------------------------- | -------------------------------------------- |
| 设计稿与素材         | 风格、构图、对象关系与目标排版         | 实际命中、动态时序、设备表现                 |
| 静态截图             | 对应版本与状态的实际合成效果           | 完整流程、异常恢复、其他内容边界             |
| 连续录屏             | 视觉时序、转场、状态变化和部分操作结果 | 未记录的触摸范围、真实资源事实与全部异常路径 |
| 可操作原型或运行观察 | 对应环境中的输入、状态和连续流程       | 未覆盖设备、版本与外部能力                   |
| 代码与契约           | 行为来源、数据归属、实现路径和约定     | 画面是否好看、真实操作是否舒适               |
| 静态检查与构建       | 格式、结构、类型或构建约束             | 审美、可读性、触摸、性能和业务结果验收       |

完成审核时明确范围、材料与版本，核对队列中的每个截图、对象、适用状态和必要方法都有对应记录，所有适用检测点都有单项结论与覆盖状态，每张输入截图都有独立实施清单，每个需调整项都有意见归属，每个待验证项都有缺口及补验动作。存在未检或待验证时明确覆盖未完成，不把“记录填完”写成“设计验收通过”。不适用项记录原因，原始问题保留到对应版本复核后再关闭。

审美共识、行为正确、运行验证和玩家理解分别给出结论；不以文档篇幅、问题数量或检查全绿代替实际覆盖。
