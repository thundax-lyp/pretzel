# 检测队列的并行执行与 parent 汇总

从 [检测点列表](review-checks.md) 按 [队列规则](review-queue.md) 建立 QUEUE.json 后再分派。每个队列项直接指向一个 `checks/<category>.md#<point-anchor>`；该点自己的方法组由一个 owner 完整执行，使用 [统一单项返回](result-contract.md)。parent 采纳单项结果后，按 [报告交付](report-output.md) 先统一意见，再逐截图展开。

## parent 与 subagent 的职责

| 阶段       | parent agent                                                      | subagent                                       |
| ---------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| 整体与拆分 | 确认输入、批次、任务和目标，先看整屏，划分对象与状态              | 接收共同上下文，不以局部裁图替代完整画面       |
| 建队列     | 从点列表选点，读取本点方法组，形成唯一条目与方法计划              | 领取明确 item_id，不自行把整页变成另一套清单   |
| 并发检测   | 分配独立条目，协调共享采集与输入环境                              | 逐项完成本点方法组，每项分别写 JSON 和单项报告 |
| 接收与汇总 | 收到结果及时写回 returned，再验收并写入 accepted 或 needs_recheck | 修正结构、补证或复查原项，不改共享队列及总报告 |
| 意见与交付 | 合并根因，生成每图动作，复看整屏与跨图关系                        | 按需复核已分配条目，不自行宣布整次审核完成     |

## 分派原则

- 默认以检测点队列项为最小责任边界，不把同一点的 M-04、M-05 分给不同 owner 后分别出报告。需要采集专家协助时，采集结果回到本项 owner，由其整合完整单项结果。
- 一个 subagent 可以批量领取多个独立项，例如同一截图的几个文字点，或同一点在几张明确截图上的多个项；仍为每个 item_id 独立返回，不能一条“首页已检查”代替。
- 根据独立项数量、材料共享性和工具能力安排并发，不为每个点机械创建一个 agent。小范围或并行工具不可用时，parent 按同一队列及返回契约串行执行。
- 截图、资源和既有录屏可以并行只读。操作同一浏览器、设备、对局或账号时指定一个采集负责人或串行时段，其他项引用带来源的采集证据。
- 有真正独立的运行环境时可并行，但分别登记环境；不把不同运行的局部证据拼成同一事件。存在前置依赖的状态按顺序采集。
- 共同上下文只提供任务、目标和已知事实；不下发必须得到的缺陷答案。parent 的整体观察可作为待解释关系，不能迫使 worker 接受其原因判断。

## 任务包

每个批次给 task-id，并列出本批 item_id；每项仍携带以下内容：

| 内容           | 要求                                                                    |
| -------------- | ----------------------------------------------------------------------- |
| 队列身份       | review_id、item_id、revision、owner 与当前条目                          |
| 目标与环境     | 当前任务、游戏类型、已确认风格、观看/输入条件及授权范围                 |
| 本点 reference | 分类文件路径与检测点锚点，直接定位该点的判据、最低证据和方法组          |
| 截图与对象     | frame_id、实际路径、SHA-256、批次、状态、object_ids 及完整画面定位      |
| 方法计划       | 本点全部必要方法、条件方法 selected/reason，必要辅助材料及采集安排      |
| 返回位置       | `results/<item-id>.json` 和同名 Markdown，字段固定见 result-contract.md |

parent 独占 QUEUE.json、DECISIONS.json、REPORT.md 和 pages。worker 只写自己所领条目的结果和明确分配的证据目录；不同项不共享可写结果文件。交叉复核同一项时明确标为复核任务，不重复计算覆盖，由原项 owner 与 parent 处理分歧。

修订或重派同项前，确认原 owner 已停止写入；确认不了时使用新 item_id 和新结果路径。关联旧项的统一意见与逐图动作一并待复核，避免结果文件和实施计划仍停在不同版本。

## 执行与返回

1. worker 核对条目、检测点节、方法计划与材料哈希，读取本点所需 `methods/<topic>.md#<method-anchor>`；不通读无关点及方法，不用分类文件中的第一个点代替当前条目。
2. 在指定对象与状态上执行整组方法，每个 selected=true 的方法都留执行记录。缺材料写 not_run，部分步骤写 partial，中断写 interrupted；已确认问题也不免除其余方法。
3. 生成固定 JSON 与从其展开的单项 Markdown；候选问题标出具体截图、对象和方法证据。只对这个点与当前条目作答。
4. 将结果文件和简短摘要返回 parent。摘要用于定位，不替代结构化结果；超时、失败、无返回或工具错误均保留执行缺口。
5. 如发现范围、适用性或方法计划有误，回报 parent 修订条目后再执行；不自行取消检测点或用不适用清空任务。

## parent 接收与收口

1. **逐项回收**：每收到一项或一个分片，核对 item_id、revision 和返回文件，立即将这些项的 returned 及 status_reason 持久化到 QUEUE.json，再进行后续验收；不等待其他 owner 或总汇总。只有摘要、缺文件、版本不符或迟到返回按队列规则记录缺口，owner 结束不等于条目 returned 或 accepted。
2. **身份与方法**：按 result-contract.md 校验字段、revision、frame_hashes 与选中方法集合；非必要额外方法不能替代缺失的必要方法。格式不合格交原 owner 修正。
3. **点结论**：结合本点判据、最低证据和完整方法组采纳或复查，及时将验收结果写回 accepted 或 needs_recheck。pass 与 complete 分别有依据；已确认偏离但方法缺证可以 adjust/incomplete。缺证不抹去已见问题，也不变成通过。
4. **冲突**：先排查截图批次、状态、尺度、规则和原证据，必要时补验；不投票、不平均分，不把多个摘要拼接当统一判断。
5. **统一意见**：对共同根因、触发与修改边界合并，保留所有来源 item_id。独立问题分别保留；参考稿修订与截图可见偏离分开。
6. **逐截图落实**：形成 DECISIONS.json 后，按每张截图实际状态写本图 action 及其直接支持 item_ids；共享根因保持一致，尺寸、布局、对象和保留点按本图具体说明。单图动作按依赖排序，每项附直接单项依据，完整检测记录另由本图索引进入。每图生成独立修改单和导航入口，包括无需改动与待验证的图。
7. **回看整体**：parent 自己复看整屏、连续流程及跨图关系，检查局部方向是否冲突；新效果未形成时只给复核计划。最终同时交付 REPORT.md 和 pages/INDEX.md。

材料发生删除或替换时按队列规则调整受影响项与 revision，不接收失效返回；未变化项保留其证据。存在必要方法、返回或证据缺口时明确覆盖未完成。并行只改变执行安排，不改变证据要求，不扩展为代码、素材、提交或发布任务。
