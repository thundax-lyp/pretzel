# 数据与结算设计

## 基础环境

持久事实使用 MySQL 8.4，会话与适用缓存使用 Redis；本阶段不接入消息队列、搜索或其他基础设施。现有系统与存储结构由 V1__init.sql 初始化。

项目初始化阶段直接维护最终结构和种子数据，不累加修补式迁移。旧环境若需要使用重新定义的初始化版本，须获得重建授权；不能通过修复迁移记录代替实际结构同步。

## 存储对象生命周期

文件引用与对象状态在同一数据库事务中维护，绑定、解绑及孤儿清理按对象加行锁后重新检查状态。分片上传按会话串行变更；完成时核对实际总字节数并保存业务引用，提交后清理分片，回滚时清理新写入的内容。HTML、SVG 等主动内容按附件返回，并禁止 MIME 嗅探。

分片会话 ID 使用不含路径语义的单段标识，只允许 1–64 位字母、数字、下划线和连字符；未提供时由服务端生成。HTTP 请求与领域值对象共同校验，禁止路径分隔符、点段和超长值映射到其他会话的分片路径。

## 游戏数据模型

以下是待实现模型，不代表已有数据库表。

- 玩家：微信身份映射、展示信息与账户状态，独立于管理账号。
- 动物配置：稳定种类标识、图鉴编号、名称、简介、视觉资源、眼睛和腿数、启用状态。
- 对局：玩家、局标识、题目序列、布局版本、状态及结算结果。
- 操作与奖励记录：幂等标识、来源、所属对局或周期、发放及消耗结果。
- 道具库存：玩家、道具类型、局外储备；局内获取额度单独记录。
- 动物收集：玩家与种类对应的解锁状态及获得数量。
- 当周计数：只存当前周业务数量；历史归档独立保存周标识与数量。

## 事务与幂等

结算在事务中确认对局未重复结束，记录消除过的种类、永久解锁和适用奖励资格。发奖与消耗使用唯一业务键，重试不能重复计数。缓存不可成为收集与榜单数量的唯一事实来源。

## 周归档

使用 Asia/Shanghai，周期为周一 00:00 至下周一 00:00（不含）。首页动物奖励领取成功时，按实际领取时刻归周，在同一事务写领取记录、累计数量、当周计数及达到当前数量的时间。永久解锁独立记录首次解锁时间，用于图鉴 NEW 标记。广场按当周领取记录查询，跨周切换展示范围。

榜单按数量降序、达到该数量的时间升序。归档保留排序所需字段。跨周新领取直接归入新周，旧周在归档提交前仍按原周可查，归档提交后由历史记录提供查询。验证任务重试、迟到领取与周边界并发。

## 体验统计

对局、奖励和收集指标从已确认业务结果产生，以对局、操作或奖励标识去重。按关卡配置版本统计通过率、有效时长和退出进度。客户端提供开局来源、分享发起及回流等交互事件。分享发起与可验证的分享结果分别记录。

## 初始化验证

新库验证应覆盖表结构、菜单访问级别和显式管理员初始化。真实数据库使用独立测试库与隔离 Redis 空间验证登录、授权、撤权和结算等流程，测试完成清理自身数据，不覆盖已部署项目数据。
