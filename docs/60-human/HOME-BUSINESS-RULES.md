## 0. 文档说明与变更

### 0.1 一句话概括

玩家**每完整通关一局**，随机获得**某一只动物的碎片 1 个**；某只动物碎片累计达到它的**兑换阈值**后，家园中该动物的**兑换按钮解锁**；点击兑换 → 服务端扣减碎片 → 通过微信小店**「创建并发送礼物」**创建礼物单（activityId=`ACTIVITY_ID`）→ 客户端用 `wx.createStoreGift` 拉起蓝包 → 玩家领取实体玩偶。

### 0.2 与历史文档的关系（重要）

| 项       | 历史口径                       | 本文口径                                              | 变更原因                                                   |
| -------- | ------------------------------ | ----------------------------------------------------- | ---------------------------------------------------------- |
| 收集单位 | 动物 1 只（`obtain_cnt`）      | **动物碎片**（`fragment_cnt`）                        | 碎片可分段累积，进度反馈更细腻，且支持"差一点"驱动         |
| 动物总数 | 328 个可收藏项（四档稀有度）   | **固定 6 只**                                         | 首期只上 6 款实体玩偶，活动 `ACTIVITY_ID` 内按活动商品发放 |
| 兑换门槛 | 统一 100 次                    | **按动物分别设定**（100 / 150 / 200）                 | 拉开价值梯度，匹配不同玩偶成本                             |
| 兑换扣减 | 不扣次数，只加 `exchanged_cnt` | **扣减碎片**（`fragment_cnt -= threshold`），余额保留 | 碎片是消耗品，扣减语义更直观                               |
| 发放方式 | 唤起小店商品页 → 用户自行下单  | **商家主动送礼（蓝包）** → 用户领取                   | 玩家不必下单付费，履约由商家侧承担                         |
| 家园列表 | 动态列表（有多少品类就多少行） | **固定 6 张卡片**，无列表聚合逻辑                     | 品类数固定，列表模式是过度设计                             |

**替换范围**：PRD 已同步升级到 **v2.5**（§3.5 整节按本文重写，四档概率与 100 次兑换口径删除），《我的动物收藏与首页展示机制设计》已升级到 **v3.0**（首页展示与自由摆放章节删除），《动物体系与奖励稀缺性分级设计》已升级到 **v3.0**（328 品类与四档稀有度作废）。三份文档已与本文对齐，不再存在「本文覆盖旧文档」的关系。

**数据迁移（已决策）**：旧 `user_animal.obtain_cnt`（328 品类聚合口径）**不做映射**——旧池无法一一对应到 6 只动物。上线时新口径从 0 起算，旧表只读留存用于历史查询，不参与本期兑换计算。

## 1. 业务概述与核心模型

### 1.1 三层结构

| 层     | 载体         | 回答的问题       | 数据落在哪                                        |
| ------ | ------------ | ---------------- | ------------------------------------------------- |
| 碎片层 | 游戏内掉落   | 我还差多少？     | `user_animal_fragment`（服务端）                  |
| 兑换层 | 家园对话框   | 我现在能不能换？ | `animal_cfg`（阈值配置） + `gift_order`（兑换单） |
| 履约层 | 微信小店礼物 | 我的玩偶到哪了？ | 微信小店（礼物单）+ 本地 `gift_order.status` 镜像 |

### 1.2 核心规则速览

| #   | 规则                   | 说明                                                                                                         |
| --- | ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| R1  | 每次过关得 1 个碎片    | 只有**完整通关（第二关清盘）**才发放，第一关清盘、失败、放弃、中途退出均不发                                 |
| R2  | 碎片归属随机           | 6 只动物按权重随机，一次只落 1 只（权重见 §3.2）                                                             |
| R3  | 碎片只增不减（除兑换） | 除兑换扣减外，任何操作都不减少碎片；不因活动结束、版本更新清零                                               |
| R4  | 阈值独立               | 6 只动物各自独立累计、独立解锁，互不转换、互不抵扣                                                           |
| R5  | 达到阈值即解锁         | `fragment_cnt >= threshold` 时该动物兑换按钮解锁                                                             |
| R6  | 兑换扣减阈值等量碎片   | 兑换 1 件扣 1 个阈值；**余额保留**，可继续累计下一件                                                         |
| R7  | 三重上限               | 单日 1 件 / 单动物累计 3 件 / 活动总库存（由小店活动控制）                                                   |
| R8  | 服务端唯一裁决         | 碎片发放、解锁判定、扣减、建单全部在服务端完成；客户端只展示，不得本地随机、不得本地扣减                     |
| R9  | 先建单后拉包           | 必须先由服务端成功创建礼物单拿到 `present_order_id`，才允许客户端拉起蓝包；顺序不可颠倒（原因见 §6.5）       |
| R10 | 幂等优先               | 关卡结算以 `round_id` 幂等；兑换以 `client_token` + `idempotent_id` 幂等，重复提交不重复扣碎片、不重复发礼物 |

### 1.3 名词定义

| 名词   | 定义                                                                                 |
| ------ | ------------------------------------------------------------------------------------ |
| 一局   | 第一关 + 第二关的完整挑战过程，一局最多产出 1 次碎片                                 |
| 过关   | 第二关牌堆与卡槽**全部清空**并判定 `clear_all_win`。第一关清盘仅进入第二关，不算过关 |
| 碎片   | 该动物专属的收集进度单位，整数，无上限                                               |
| 阈值   | 兑换 1 件该动物实体玩偶所需碎片数（`animal_cfg.threshold`）                          |
| 可兑换 | 碎片满足阈值 + 通过三重上限校验 + 商品在售                                           |
| 礼物单 | 微信小店侧的一次送礼记录，由「创建并发送礼物」接口生成，主键 `present_order_id`      |
| 蓝包   | 客户端礼物领取组件（`wx.createStoreGift` 返回的 `StoreGift` 实例）                   |

## 2. 首页「家园」入口交互流程

### 2.1 按钮定义

| 项     | 规范                                                                                                  |
| ------ | ----------------------------------------------------------------------------------------------------- |
| 位置   | 首页底部右侧按钮组，自左向右第一枚（家园 / 排行榜 / 分享）                                            |
| 类型   | 次级按钮，尺寸与其他次按钮一致                                                                        |
| 角标   | 显示**当前可兑换的动物只数**（0–6）。为 0 时不显示角标；大于 0 显示数字并带一次呼吸动效（进入首页时） |
| 点击态 | 按下缩放 0.96 + 触感反馈（`wx.vibrateShort({type:'light'})`）                                         |

> 角标口径变更：旧版为"已收藏品类数"，本期 6 只动物固定，收藏数恒为 6，无信息量；改为"可兑换只数"直接指向行动。

### 2.2 点击时序（打开家园）

```
玩家点击「家园」
  ├─ ① 300ms 防抖：若 isOpening 为 true，直接 return（不重复弹窗）
  ├─ ② 播放按钮音效 + 触感反馈
  ├─ ③ 立即打开家园对话框骨架（6 张卡片占位，灰色头像块）
  │      └─ 有本地缓存（home_panel_cache）→ 先用缓存值填充进度与按钮态
  ├─ ④ 并发请求 GET /api/v1/home/panel（超时 3s）
  │      ├─ 成功 → 整体覆盖渲染，200ms 淡入，写回 home_panel_cache
  │      ├─ 失败但有缓存 → 保留缓存渲染 + 顶部提示条"网络异常，点击重试"
  │      └─ 失败且无缓存 → 加载失败态 + "重试"按钮，所有兑换按钮置灰
  └─ ⑤ 关闭对话框 → 关闭动画 200ms → 回到首页 → isOpening = false
```

**关键约束**

1. 打开对话框**不阻塞首页渲染**，不出现全屏 loading。
2. 对话框打开期间**暂停首页装饰动效的计时器**（降低后台功耗），关闭后恢复；首页不承载动物，无动物动效需要处理。
3. 对话框打开期间若收到结算播报（如从胜利框跳转而来），进度以接口返回为准，不用本地值覆盖。

### 2.3 家园对话框结构

```
┌──────────────────────────────────────────────────────┐
│ 兑换记录                         家园         ✕      │
│ 已兑换 2 只 · 累计 386 个碎片                          │
├──────────────────────────────────────────────────────┤
│ ┌────────┐  吉娃娃            碎片 100 / 100          │
│ │ 头像   │  ──────────────────────────  100%        │
│ │        │                        [  兑 换  ]  ← 高亮 │
│ └────────┘                                          │
│ ┌────────┐  卡皮巴拉           碎片  87 / 200         │
│ │ 头像   │  ────────░░░░░░░░░░░░░░░   44%           │
│ │        │                        还差 113 个  [兑换] │
│ └────────┘                                          │
│ ...（共 6 张，固定顺序，纵向滚动）                     │
└──────────────────────────────────────────────────────┘
```

| 区域     | 元素          | 规格                                                                                                    |
| -------- | ------------- | ------------------------------------------------------------------------------------------------------- |
| 左上     | "兑换记录"    | 打开兑换记录对话框                                                                                      |
| 顶部中   | 标题          | "家园"                                                                                                  |
| 顶部右   | 关闭          | 关闭对话框                                                                                              |
| 标题下方 | 汇总          | "已兑换 N 只 · 累计 M 个碎片"（N = 已成功领取过的动物数，M = 历史累计获得碎片数 `total_obtained` 求和） |
| 卡片左   | 动物头像      | 96×96 圆角；未解锁时可加 30% 灰度但**不得变剪影**（要让玩家看清目标）                                   |
| 卡片中   | 名称 + 进度条 | 进度条 `min(fragment_cnt/threshold, 1)`；文字"碎片 x / 阈值"                                            |
| 卡片右下 | 兑换按钮      | 五态见 §4.4                                                                                             |
| 卡片底部 | 副文案        | 未解锁："还差 N 个碎片"；已解锁："可兑换"；已兑完："已兑换 X 件"                                        |

**排序**：固定顺序（`animal_cfg.sort`），不按进度排序——固定位置便于玩家形成肌肉记忆，进度变化不会导致卡片跳位。

### 2.4 兑换确认对话框

| 项       | 规则                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 触发     | 点击可用态兑换按钮                                                                                                            |
| 内容     | 动物头像 + 名称 + "将消耗 150 个碎片兑换 1 只实体玩偶" + "剩余碎片 160 → 10" + "由微信小店发货，领取后需在蓝包内填写收货信息" |
| 主按钮   | "确认兑换" → 调 `POST /api/v1/gift/redeem`                                                                                    |
| 次按钮   | "取消" → 关闭，不发起请求，不消耗碎片                                                                                         |
| 二次确认 | 需要（涉及资产消耗 + 实体履约，不做无确认直兑）                                                                               |

### 2.5 兑换后即时反馈

1. 主按钮转 loading（文案"兑换中…"），禁用整个对话框的兑换按钮，防连点。
2. 接口成功返回 `present_order_id` → 关闭确认框 → **立即调用 `wx.createStoreGift` 拉起蓝包**。
3. 蓝包拉起成功：家园卡片进度立即刷新为扣减后的值，按钮回到"还差 N 个碎片"。
4. 蓝包拉起失败（`isSupported() === false` 或 `open()` reject）：卡片仍刷新，同时 Toast "礼物已发放，可在微信「我-服务-微信小店」或稍后重新进入家园领取"。
5. 接口失败：不关闭确认框，Toast 具体原因（见 §6.8 文案表），**不本地扣减**。

## 3. 碎片获取规则

### 3.1 触发条件

| 场景                             | 是否发放    | 备注                              |
| -------------------------------- | ----------- | --------------------------------- |
| 第二关清盘 `clear_all_win`       | **发 1 个** | 唯一发放路径                      |
| 第一关清盘 → 进入第二关          | 不发        | 结算返回 `gained_fragment = null` |
| 卡槽满 7 格判负 `slot_full_lose` | 不发        | —                                 |
| 主动放弃挑战                     | 不发        | —                                 |
| 切后台超时 / 进程被杀            | 不发        | 本局作废                          |
| 同一 `round_id` 重复上报         | 只发一次    | 幂等，第二次返回首次结果          |

**判定位置**：`POST /api/v1/round/finish`，`result = clear_all_win` 且 `level = 2` 时由服务端执行掉落。

### 3.2 随机抽取规则

**口径说明**：需求描述为"随机获得某一只动物的碎片各一个"，本文按**每次过关 → 随机命中 1 只动物 → 该动物碎片 +1** 实现（`fragment_per_pass = 1`）。配置项 `animal_drop.grant_mode` 支持 `single`（默认）与 `all`（每只各 +1）两种模式，若要改为后者需同步下调阈值，否则产出速率放大约 6 倍（见 §3.5 经济性测算）。

**权重表（默认上线方案：均衡型）**

| 动物     | `animal_id`     | 阈值 | 权重（万分比） | 单次命中概率 | 期望集满所需过关数 |
| -------- | --------------- | ---- | -------------- | ------------ | ------------------ |
| 吉娃娃   | `dog_chihuahua` | 100  | 1176           | 11.76%       | **850**            |
| 公仔猫   | `cat_plush`     | 100  | 1176           | 11.76%       | **850**            |
| 小黄鸭   | `duck_yellow`   | 150  | 1765           | 17.65%       | **850**            |
| 鸡肚猪   | `pig_jidu`      | 150  | 1765           | 17.65%       | **850**            |
| 招财羊   | `sheep_fortune` | 150  | 1765           | 17.65%       | **850**            |
| 卡皮巴拉 | `capybara`      | 200  | 2353           | 23.53%       | **850**            |
| 合计     | —               | 850  | **10000**      | 100%         | —                  |

**权重设计逻辑**

1. `weight_i ∝ threshold_i`，即概率与阈值同比例放大，**每只动物的期望达成周期完全一致（≈850 次过关）**，阈值差异只体现为"一次要攒更多"，不体现为"某只永远集不满"。
2. 若采用"高阈值低概率"，卡皮巴拉（阈值 200）在 8% 权重下期望 2500 次过关，实际不可达，会造成"永远差一只"的负面体验。
3. 权重按万分比取整，总和精确等于 10000，便于服务端 `rand(1..10000)` 区间命中，避免浮点比较。

**备选方案（稀缺型，仅供运营切换）**

| 动物     | 阈值 | 权重 | 概率 | 期望过关 | 与均衡型对比                 |
| -------- | ---- | ---- | ---- | -------- | ---------------------------- |
| 吉娃娃   | 100  | 2000 | 20%  | 500      | 更快                         |
| 公仔猫   | 100  | 2000 | 20%  | 500      | 更快                         |
| 小黄鸭   | 150  | 1800 | 18%  | 833      | 持平                         |
| 鸡肚猪   | 150  | 1700 | 17%  | 882      | 持平                         |
| 招财羊   | 150  | 1700 | 17%  | 882      | 持平                         |
| 卡皮巴拉 | 200  | 800  | 8%   | 2500     | **显著更难，不建议首期使用** |

**抽取算法（服务端）**

```python
def roll_fragment(openid, round_id):
    # 1. 取当前生效的掉落配置（含活动时间窗、日上限）
    cfg = load_drop_cfg()
    if not cfg.enabled: return None          # 长期活动：只看开关，不看截止日期
    if daily_fragment_cnt(openid, today()) >= cfg.daily_cap:   # 默认 60
        return None                                            # 超上限静默不发

    # 2. 排除不可发放项（商品下架 / 兑换已满 3 件）
    pool = [a for a in cfg.items if a.status == 'on' and not is_maxed(openid, a)]
    if not pool: return None

    # 3. 权重区间命中
    total = sum(a.weight for a in pool)
    r = randint(1, total)
    acc = 0
    for a in pool:
        acc += a.weight
        if r <= acc: chosen = a; break

    # 4. 原子累加
    UPSERT user_animal_fragment(openid, chosen.animal_id)
      SET fragment_cnt = fragment_cnt + 1, total_obtained = total_obtained + 1
    INSERT fragment_log(openid, animal_id, delta=+1, reason='round_finish', round_id)

    return {'animal_id': chosen.animal_id, 'added': 1,
            'fragment_cnt_after': ..., 'threshold': chosen.threshold,
            'unlocked': fragment_cnt_after >= chosen.threshold}
```

**强制约束**

- 随机数必须服务端生成，禁止下发概率表到客户端。
- 客户端**不得**展示具体概率数值，只展示掉落结果。
- 权重、池子、日上限均在服务端配置，支持热更，但改动需记录审计日志。

### 3.3 防刷与发放上限

| 项                 | 限制                                              | 超限表现                                           |
| ------------------ | ------------------------------------------------- | -------------------------------------------------- |
| 单账号单日碎片上限 | 60 个（可配）                                     | 继续正常通关，但结算不返回碎片，胜利框不显示碎片区 |
| 单账号单日通关次数 | 由现有反作弊规则约束（时长 / 步数校验）           | 判负或拒绝结算                                     |
| 单局最多产出       | 1 个                                              | 一局无论清盘多少次都只发 1 次                      |
| 碎片不可转移       | 仅绑定 openid，不可赠送、不可交易、不可跨账号合并 | —                                                  |
| 异常设备 / 模拟器  | 命中风控则不发碎片且回报 `risk` 标记              | 静默不发，不提示                                   |

### 3.4 结算响应与胜利框展示

`POST /api/v1/round/finish` 返回新增字段：

```json
    "code": 0,
    "msg": "ok",

        "gained_fragment": {
```

胜利框新增"碎片"区域：

| 元素     | 规则                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------- |
| 展示     | 动物头像 + 名称 + "碎片 88 / 200" + 进度条动画（从旧值滚到新值，600ms）                              |
| 文案     | `added=1` 时"获得 1 个卡皮巴拉碎片"；`gained_fragment=null` 且超日上限时"今日碎片已达上限，明日再来" |

### 3.5 经济性测算与调参建议

以"单次 1 个碎片、均衡型权重"为基准：

| 玩家日均过关 | 首次兑换（850 次过关） | 集齐 6 只（≈950–1050 次过关） |
| ------------ | ---------------------- | ----------------------------- |
| 10 次        | ≈85 天                 | ≈95–105 天                    |
| 20 次        | ≈43 天                 | ≈48–53 天                     |
| 40 次        | ≈21 天                 | ≈24–27 天                     |

**结论**：当前阈值 + 权重组合下，单个玩偶的期望获取周期落在 **3 周到 3 个月**区间，适合"长线留存 + 实体奖励"的定位；若希望压缩到 2–4 周，推荐只调一个参数：

| 调参项              | 现值        | 建议值       | 效果                                            |
| ------------------- | ----------- | ------------ | ----------------------------------------------- |
| `fragment_per_pass` | 1           | **2 或 3**   | 周期缩短至 1/2 或 1/3（850 → 425 / 283 次过关） |
| 阈值整体下调        | 100/150/200 | 不建议动     | 阈值是玩家可感知的"目标刻度"，频繁改会破坏信任  |
| 权重改为稀缺型      | 均衡型      | 不建议首期用 | 卡皮巴拉不可达                                  |

> 该测算已被产品确认为**设计值**（§12 决策 3），权重、阈值、`fragment_per_pass` 均不再调整。

## 4. 兑换阈值表与解锁判定

### 4.1 兑换阈值表

| 序号 | 动物名称 | `animal_id`     | 兑换阈值（碎片） | 难度档 | 对应实体玩偶     |
| ---- | -------- | --------------- | ---------------- | ------ | ---------------- |
| 1    | 吉娃娃   | `dog_chihuahua` | **100**          | 入门   | 吉娃娃毛绒挂件   |
| 2    | 公仔猫   | `cat_plush`     | **100**          | 入门   | 公仔猫毛绒玩偶   |
| 3    | 小黄鸭   | `duck_yellow`   | **150**          | 进阶   | 小黄鸭毛绒玩偶   |
| 4    | 鸡肚猪   | `pig_jidu`      | **150**          | 进阶   | 鸡肚猪毛绒玩偶   |
| 5    | 招财羊   | `sheep_fortune` | **150**          | 进阶   | 招财羊毛绒玩偶   |
| 6    | 卡皮巴拉 | `capybara`      | **200**          | 困难   | 卡皮巴拉毛绒玩偶 |

**阈值设计要点**

1. 100 / 150 / 200 三档，形成 1 : 1.5 : 2 的清晰梯度，玩家一眼能分辨"哪个更贵"。
2. 100 与 150 之间留 50 的间隔、150 与 200 之间留 50，避免"差一点点却差很多"的挫败。
3. 阈值是**配置项**，不硬编码；调整阈值只影响后续判定，已获得的碎片和已兑换记录不受影响（见 §5.4 兼容说明）。
4. 阈值只影响解锁，不参与掉落，因此调阈值不需要重启活动。

**关于商品与 SKU（已决策）**

建单接口只需 `activity_id`（`ACTIVITY_ID`），**业务侧不维护 `product_id` / `sku_id`**：

- 6 款玩偶在活动 `ACTIVITY_ID` 内配置，由活动决定发放哪个商品；游戏侧不感知商品编号。
- `create_present_order` 的入参中 `product_id` / `sku_id` 为平台必填项时，由服务端在调用前从**活动配置**（`game_config` 中的活动快照）注入，**不落业务表、不进 `animal_cfg`**。
- 若平台支持活动内多商品自动匹配，则完全不传；具体以联调实测结果为准（见 §12 决策 4）。

### 4.2 解锁判定逻辑

```python
def eval_card(openid, animal, cfg, now):
    frag      = get_fragment(openid, animal.id) or 0
    threshold = animal.threshold

    # ① 碎片门槛
    enough = frag >= threshold
    # ② 单日上限（自然日 00:00 重置，按 Asia/Shanghai）
    today_cnt = count_orders(openid, animal.id=None, date=today(now), exclude_cancelled=True)
    daily_ok  = today_cnt < 1
    # ③ 单动物累计上限
    total_cnt = count_orders(openid, animal.id=animal.id, exclude_failed=True)
    total_ok  = total_cnt < 3
    # ④ 商品与活动状态（长期活动：只看开关与剩余份数，不看截止日期）
    sale_ok   = animal.status == 'on' and activity_enabled() and activity_stock_left() > 0

    unlocked = enough and daily_ok and total_ok and sale_ok
    return {
        'fragment_cnt': frag,
        'threshold': threshold,
        'progress': round(min(frag / threshold, 1), 4),
        'short_of': max(threshold - frag, 0),      # 还差多少个
        'redeemable': enough and daily_ok and total_ok and sale_ok,
        'today_redeemed': today_cnt,
        'total_redeemed': total_cnt,
        'block_reason': None if unlocked else pick_reason(enough, daily_ok, total_ok, sale_ok)
    }
```

**判定必须满足的五个条件（全部为真才解锁）**

| #   | 条件     | 表达式                                            | 不满足时的按钮文案 |
| --- | -------- | ------------------------------------------------- | ------------------ |
| C1  | 碎片达标 | `fragment_cnt >= threshold`                       | "还差 N 个碎片"    |
| C2  | 今日未兑 | `today_redeemed == 0`                             | "今日已达上限"     |
| C3  | 累计未满 | `total_redeemed < 3`                              | "已兑换 3 件"      |
| C4  | 商品在售 | `status=on` 且活动仍有可发份数                    | "暂不可兑换"       |
| C5  | 活动开关 | `activity.enabled = true`（长期活动，无截止日期） | "活动已暂停"       |

> 判定优先级：C1 → C2 → C3 → C4 → C5。展示时只显示优先级最高的那条原因，避免文案叠加。

## 5. 碎片扣减、重复兑换与兑换单状态机

### 5.1 扣减规则

| 项       | 规则                                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------- |
| 扣减量   | 等于该动物 `threshold`（100 / 150 / 200）                                                                      |
| 扣减时机 | **服务端创建礼物单成功后**在同一业务流程内扣减；建单失败则回滚（详见 §6.6 补偿事务）                           |
| 余额保留 | `fragment_cnt_after = fragment_cnt_before - threshold`，**不清零**                                             |
| 扣减下限 | 扣减前后均保证 `fragment_cnt >= 0`；通过 `UPDATE ... WHERE fragment_cnt >= threshold` 的条件更新保证不出现负数 |
| 并发安全 | 行级锁 + 条件更新，重复请求只会成功一次                                                                        |
| 流水     | 每次扣减写一条 `fragment_log`（`delta = -threshold`）                                                          |

**示例**

| 场景             | 扣减前 | 阈值 | 扣减后     | 进度条         |
| ---------------- | ------ | ---- | ---------- | -------------- |
| 刚好达标         | 100    | 100  | **0**      | 0%             |
| 略有溢出         | 103    | 100  | **3**      | 3%             |
| 大额溢出         | 460    | 200  | **260**    | 100%（仍可兑） |
| 余额不足（被拒） | 99     | 100  | 99（不变） | 99%            |

### 5.2 重复兑换限制

| #   | 限制                             | 默认值                                                 | 超限返回                     | 目的                        |
| --- | -------------------------------- | ------------------------------------------------------ | ---------------------------- | --------------------------- |
| L1  | 单动物累计兑换件数               | 3 件 / 账号                                            | `1007`                       | 控制单 SKU 成本与被转卖风险 |
| L2  | 单账号单日兑换件数（全动物合计） | 1 件 / 天                                              | `1008`                       | 抑制机器刷量与集中下单      |
| L3  | 活动总份数                       | 由小店活动 `ACTIVITY_ID` 预设                          | `1004`（映射小店 `SHOP_ID`） | 预算硬上限                  |
| L4  | 活动时间窗                       | 以小店活动起止为准                                     | `1009`                       | 到期关闸                    |
| L5  | 单账号累计兑换件数（全动物）     | 6 件 / 账号（= 每种各 1 件上限的组合上限，可按预算调） | `1010`                       | 全局兜底                    |

> L1 与 L5 同时生效时取更严格者。L2 的"自然日"以服务端 `Asia/Shanghai` 00:00 为界，不用客户端本地时间。

### 5.3 兑换单状态机

```
                    ┌─────────┐
                    │  init   │  本地已建单，尚未拿到 present_order_id
                    └────┬────┘
            建单成功      │      建单明确失败（库存/参数/风控）
        ┌───────────────┴───────────────┐
        ▼                               ▼
  ┌───────────┐                   ┌──────────┐
  │  created  │ 已建单，待领取      │  failed  │ 碎片已回滚
  └─────┬─────┘                   └──────────┘
        │ 用户收下（orderStatus 20 / sub_order 12→20）
        ▼
  ┌───────────┐
  │ received  │ 已领取，待发货
  └─────┬─────┘
        │ sub_order 21 / 30
        ▼
  ┌───────────┐
  │  shipped  │ 已发货 / 待收货
  └─────┬─────┘
        │ sub_order 100
        ▼
  ┌───────────┐
  │   done    │ 完成
  └───────────┘

  旁路终态：expired（180 未领取过期）/ refunded（181 超时退款）
            cancelled（250 用户取消 / 200 平台取消售后退款）
  异常态：unknown（建单请求超时，结果未知，由补偿任务收敛）
```

**状态与碎片的关系**

| 终态                             | 是否返还碎片 | 是否计入 L1/L2 次数 | 说明                                 |
| -------------------------------- | ------------ | ------------------- | ------------------------------------ |
| `done`                           | 否           | 是                  | 正常履约                             |
| `shipped` / `received`           | 否           | 是                  | 履约中                               |
| `expired`（180）                 | **是**       | 否                  | 未履约，退还，避免玩家白扣           |
| `refunded`（181）                | **是**       | 否                  | 未履约，退还                         |
| `cancelled`（250，用户主动取消） | **是**       | **是**              | 退还但计次，防"取消-重兑"刷单绕过 L2 |
| `cancelled`（200，平台取消）     | **是**       | 否                  | 平台原因，全额退                     |
| `failed`（建单失败）             | 已回滚       | 否                  | 事务内保证一致                       |

### 5.4 阈值调整的兼容说明

若运营中途修改某动物阈值（如 100 → 120）：

- **已持有碎片不变**（碎片是资产）。
- **已成功兑换的记录不重算**（历史不追溯）。
- **L1 累计件数不重算**。
- 若阈值上调，原本可兑换的卡片会重新变为 `locked`，属于预期行为；需在改动前评估舆论风险，建议活动期内冻结阈值。

| 6011100           | 活动类型错误                | 否                  | 活动配置错误，回滚 + 告警                                 |
| 6011102           | 祝福语长度超限              | 否                  | 截断文案后**重试 1 次**；仍失败则回滚                     |
| 6011103           | 活动侧全 SKU 库存不足       | 否                  | 回滚，提示"活动奖品已发完"                                |
| 6011104           | 相同幂等 ID 并发处理中      | **是**              | 退避 800ms 后重试（最多 3 次）                            |
| SHOP_ID           | 送礼份数超出活动预设库存    | 否                  | 回滚，提示"活动奖品已发完"，同步关闭活动开关              |
| 6080061           | 商品与活动配置不匹配        | 否                  | 配置错误，回滚 + 高优告警                                 |
| 其他 / 超时 / 5xx | 结果未知                    | **是（同幂等 ID）** | 走 §6.7 的 `unknown` 收敛流程                             |

### 6.3 接口二：`wx.createStoreGift`（客户端拉起蓝包）

| 项           | 内容                                                                                          |
| ------------ | --------------------------------------------------------------------------------------------- |
| 用途         | 在客户端创建**蓝包组件实例**，用于展示并领取已由服务端创建好的礼物                            |
| 调用方       | 客户端（小游戏）                                                                              |
| 调用时机     | `POST /gift/redeem` 成功返回 `present_order_id` 之后                                          |
| 基础库要求   | **≥ 3.8.12**，低版本需兼容处理                                                                |
| 微信版本要求 | iOS ≥ 8.0.60，Android ≥ 8.0.60                                                                |
| 环境限制     | **不支持**微信 Windows / Mac 版小程序、小游戏；鸿蒙 OS 版支持                                 |
| 官方文档     | https://developers.weixin.qq.com/minigame/dev/api/open-api/store-gift/wx.createStoreGift.html |

**入参**

| 参数             | 类型                                         | 必填 | 说明                                                                                                                                        |
| ---------------- | -------------------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `presentOrderId` | boolean（文档标注有误，**实际应为 string**） | 否   | 礼物订单 ID，即服务端 `create_present_order` 返回的 `present_order_id`。文档类型标注为 boolean 属官方笔误，实际传字符串，需在接入时实测确认 |
| `openid`         | string                                       | 否   | 当前用户 openid。建议**不传**，由微信按当前登录态自动匹配，减少"非收礼人"（606662）报错                                                     |

**返回值 `StoreGift` 对象**

| 方法             | 返回                                  | 说明                                                                   |
| ---------------- | ------------------------------------- | ---------------------------------------------------------------------- |
| `isSupported()`  | boolean                               | 当前环境是否支持礼物组件。**必须先判断**，false 时不调用 `open()`      |
| `getOrderInfo()` | `Promise<{orderStatus, wishMessage}>` | 查询订单状态。`orderStatus` 取值见下表；失败走 `catch`，`errCode` 见下 |
| `open()`         | `Promise`                             | 打开礼物界面。**注意：回调仅代表"界面已打开"，不代表"已收下礼物"**     |

**`orderStatus` 取值**

| 值  | 含义                       | 客户端处理                     |
| --- | -------------------------- | ------------------------------ |
| 10  | 支付成功，用户可以领取礼物 | 显示"待领取"，可再次 `open()`  |
| 20  | 礼物已经领取               | 置为已领取，触发服务端状态同步 |
| 180 | 礼物超时未领取             | 提示已过期，服务端退碎片       |
| 181 | 超时退款                   | 同上                           |
| 250 | 订单已取消                 | 提示已取消，服务端退碎片       |

**`getOrderInfo()` 异常**

| errCode  | 含义                     | 处理                                                    |
| -------- | ------------------------ | ------------------------------------------------------- |
| 40097    | 参数错误（订单 ID 不对） | 校验本地存的 `present_order_id`；无效则丢弃并重新拉面板 |
| 606662   | 当前用户非收礼人         | 提示"该礼物不属于当前账号"，服务端核对 openid 一致性    |
| 其他非 0 | 拉取失败                 | 降级为服务端 `get_present` 查询                         |

**客户端调用骨架**

```javascript
async function openGift(presentOrderId) {
    if (!wx.createStoreGift) return { ok: false, reason: "api_unavailable" };

    const gift = wx.createStoreGift({ presentOrderId: String(presentOrderId) });

    if (!gift.isSupported()) return { ok: false, reason: "unsupported" };

    try {
        const before = await gift.getOrderInfo();
        if (before.orderStatus === 20) return { ok: true, status: "received" };
        if ([180, 181, 250].includes(before.orderStatus))
            return { ok: true, status: "closed" };

        await gift.open(); // 仅代表界面打开
        // 打开后轮询：3 次，间隔 2s / 4s / 8s
        for (const delay of [2000, 4000, 8000]) {
            await wait(delay);
            const info = await gift.getOrderInfo();
            if (info.orderStatus === 20)
                return { ok: true, status: "received" };
        }
        return { ok: true, status: "pending" }; // 用户未完成领取，下次进来可继续
    } catch (e) {
        return { ok: false, reason: e.errCode, msg: e.errMsg };
    }
}
```

### 6.4 接口三：查询礼物订单详情（`get_present`）

| 项         | 内容                                                                                                                          |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 用途       | **服务端**查询某笔礼物单的权威状态（领取 / 发货 / 完成 / 过期 / 取消），是状态镜像的唯一可信来源                              |
| 调用方     | 仅服务端 `game-api`                                                                                                           |
| 方法 / URL | `POST https://api.weixin.qq.com/channels/ec/order/present/get?access_token=ACCESS_TOKEN`                                      |
| 调用时机   | ① 客户端回调"已领取"后同步一次；② 兑换记录页打开时批量刷新；③ 定时任务每小时回收 7 日内未终态订单；④ `unknown` 订单的补偿收敛 |
| 官方文档   | https://developers.weixin.qq.com/doc/store/shop/API/miniandstore/cooperation_gift/api_get_present                             |

**请求参数**

| 参数               | 类型   | 必填 | 说明                                                           |
| ------------------ | ------ | ---- | -------------------------------------------------------------- |
| `access_token`     | string | 是   | query 参数                                                     |
| `present_order_id` | string | 是   | 礼物单 ID（**字符串**，注意大整数精度，禁止用 JS number 处理） |

**返回参数**

| 字段                                            | 类型            | 说明                                                        |
| ----------------------------------------------- | --------------- | ----------------------------------------------------------- |
| `errcode` / `errmsg`                            | number / string | 0 为成功                                                    |
| `present.present_order_id`                      | string          | 礼物单 ID                                                   |
| `present.create_time`                           | number          | 创建时间（秒级时间戳）                                      |
| `present.is_b2c_free_present`                   | boolean         | 是否付款。`0` 已付款、`1` 无需付款（商家自送场景通常为 1）  |
| `present.activity_id`                           | string          | 关联活动 ID，应为 **"ACTIVITY_ID"**，可用于核对配置是否正确 |
| `present.present_detail.price_info.order_price` | number          | 礼物单价格（分）                                            |
| `present.present_detail.pay_info.pay_time`      | number          | 支付时间                                                    |
| `present.present_detail.wishmessage`            | string          | 祝福语，与建单时传入一致，可用于校验                        |
| `present.sub_order_list[].order_id`             | string          | 子单订单 ID（发货/物流以此为准）                            |
| `present.sub_order_list[].openid`               | string          | 收礼者 openid                                               |
| `present.sub_order_list[].status`               | number          | 子单状态，枚举见下                                          |

**子单 `status` 枚举与本地映射**

| 子单 status | 含义                       | 本地 `gift_order.status`  |
| ----------- | -------------------------- | ------------------------- |
| 12          | 礼物待收下                 | `created`                 |
| 20          | 待发货                     | `received`                |
| 21          | 部分发货                   | `shipped`                 |
| 30          | 待收货                     | `shipped`                 |
| 100         | 完成                       | `done`                    |
| 180         | 礼物单过期                 | `expired`（触发退碎片）   |
| 200         | 全部商品售后之后，订单取消 | `cancelled`（触发退碎片） |

**错误码**

| errcode | 含义         | 处理                                                                    |
| ------- | ------------ | ----------------------------------------------------------------------- |
| 0       | 成功         | —                                                                       |
| 6080077 | 礼物单号错误 | 视为无效单，标记 `invalid` 并告警（通常是 `present_order_id` 存错类型） |
| 其他    | 通用错误     | 按指数退避重试 3 次，仍失败则保持原状态，下轮再刷                       |

> **`get_present` 与 `getOrderInfo` 的分工**：客户端 `getOrderInfo` 只用于**即时交互反馈**（快、但不含发货信息）；服务端 `get_present` 是**权威状态源**（含子单、发货、活动归属）。二者冲突时**以 `get_present` 为准**。

### 6.5 调用顺序与"不可颠倒"的原因

**固定顺序：兑换接口 → 建单接口 → 拉起蓝包 → 查询状态**

| 步骤 | 动作                                              | 不可省略/颠倒的原因                                                                      |
| ---- | ------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 1    | `POST /gift/redeem` 校验 + 扣碎片 + 建单          | 若先扣碎片后建单失败，靠补偿回滚；若先建单后扣碎片，会出现"礼物已发但碎片没扣"的超发漏洞 |
| 2    | `create_present_order` 拿 `present_order_id`      | 蓝包**必须**有礼物单才能打开，无单可拉                                                   |
| 3    | `wx.createStoreGift` + `isSupported()` + `open()` | 若客户端先拉起组件再等服务端建单，组件拿不到单号必然失败，且用户看到"礼物不存在"         |
| 4    | `getOrderInfo` 轮询 → `get_present` 校准          | `open()` 回调只代表界面打开，不代表领取成功，必须以状态码判定                            |

**特别注意**

1. **`open()` 的 Promise resolve ≠ 领取成功**。必须用 `getOrderInfo().orderStatus === 20` 或服务端 `get_present` 子单状态确认。
2. **禁止在客户端生成或猜测 `present_order_id`**。
3. **禁止把 `present_order_id` 当作幂等键**：它是结果，不是请求键。
4. **`present_order_id` 与 `order_id` 都要按字符串处理**（19 位量级，超出 JS 安全整数范围）。

### 6.6 扣减—建单的补偿事务（跨系统一致性）

建单是跨系统调用，无法与数据库事务同生共死，采用"**先占后调、失败补偿**"：

```
事务A（本地 DB，短事务）
  1. SELECT ... FOR UPDATE 碎片行
  2. 校验 C1–C5、L1–L5（含今日/累计件数查询）
  3. INSERT gift_order(status='init', exchange_no, client_token, idempotent_id)
  4. UPDATE user_animal_fragment
        SET fragment_cnt = fragment_cnt - threshold
      WHERE openid=? AND animal_id=? AND fragment_cnt >= threshold
     → 影响行数必须为 1，否则 ROLLBACK 并返回 1004
  5. INSERT fragment_log(delta = -threshold, reason='redeem')
COMMIT

事务B（调用微信）
  create_present_order(...)

分支：
  ├─ errcode = 0
  │    事务C: UPDATE gift_order SET present_order_id=?, status='created', called_at=now()
  │           返回客户端 {present_order_id, status:'created', fragment_after}
  ├─ errcode ∈ {108001, 108002, 40097, 608010, ...}（明确失败）
  │    事务D: UPDATE gift_order SET status='failed', errcode=?, errmsg=?
  │           UPDATE user_animal_fragment SET fragment_cnt = fragment_cnt + threshold（回滚）
  │           INSERT fragment_log(delta = +threshold, reason='redeem_rollback')
  │           返回客户端错误
  └─ 超时 / 5xx / 网络异常（结果未知）
       事务E: UPDATE gift_order SET status='unknown', retry_cnt=0
              不立即回滚碎片（可能已在微信侧成功）
              返回客户端 {code: 1011, msg:'兑换处理中，请稍后在兑换记录查看'}
              补偿任务接手（§6.7）
```

**为什么"未知"不立即回滚**：若微信侧其实已建单成功而我们回滚了碎片，会出现"礼物已发、碎片还在"的超发。宁可让用户等 1 分钟，也不可超发。

### 6.7 幂等与重试策略

**幂等键设计**

| 层级         | 键              | 生成方                                                  | 作用                                             |
| ------------ | --------------- | ------------------------------------------------------- | ------------------------------------------------ |
| 客户端请求级 | `client_token`  | 客户端（UUID v4，一次兑换生成一次，存在内存与本地缓存） | 防用户连点 / 弱网重试导致重复提交                |
| 服务端订单级 | `exchange_no`   | 服务端（`EX` + yyyyMMdd + 6 位序号）                    | 业务单号，展示与对账                             |
| 微信侧       | `idempotent_id` | 服务端 = `sha1(openid + animal_id + exchange_no)`       | 让微信侧对同一请求去重，超时重试不会产生两份礼物 |

**重试矩阵**

| 失败类型                           | 是否重试   | 重试次数 | 退避                    | 备注                                |
| ---------------------------------- | ---------- | -------- | ----------------------- | ----------------------------------- |
| 网络超时（无响应）                 | 是         | 3        | 300ms / 800ms / 2000ms  | 同 `idempotent_id`                  |
| HTTP 5xx                           | 是         | 3        | 同上                    | 同上                                |
| `6011104`（幂等并发中）            | 是         | 3        | 800ms / 1500ms / 3000ms | 必须先退避，立刻重试仍会撞          |
| `6011102`（祝福语超长）            | 是（1 次） | 1        | 无                      | 截断到 100 字符后重试               |
| 库存 / 风控 / 配置类（108001 等）  | 否         | —        | —                       | 直接失败并回滚                      |
| access_token 失效（40001 / 42001） | 是         | 1        | 立即                    | 强刷 token 后重试一次，仍失败则告警 |
| 客户端 `open()` 失败               | 是         | 用户手动 | —                       | 卡片进入 `cooldown`，点"去领取"重拉 |

**`unknown` 订单收敛（定时任务，每 30s 扫描一次）**

```
for order in gift_order where status='unknown' and retry_cnt < 20:
    # 用同一 idempotent_id 重放建单请求
    r = create_present_order(..., idempotent_id=order.idempotent_id)
    if r.errcode == 0:
        order.present_order_id = r.present_order_id
        order.status = 'created'
    elif r.errcode == 6011104:
        order.retry_cnt += 1; continue          # 仍在处理，稍后再来
    elif r.errcode in HARD_FAIL:
        rollback_fragment(order)                # 确认失败，退碎片
        order.status = 'failed'
    else:
        order.retry_cnt += 1

# 超过 20 次或超过 24h 仍未收敛 → status='failed_manual'，人工介入
```

### 6.9 access_token 与安全

| 项       | 规范                                                                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 获取方式 | 服务端用**小游戏 AppID + AppSecret** 调稳定版 `/cgi-bin/stable_token`，`grant_type=client_credential`                                                |
| 缓存     | Redis 单键缓存，提前 5 分钟刷新；进程内二级缓存 60s，避免每单都取                                                                                    |
| 失效处理 | 返回 40001 / 42001 时强刷一次并重试；连续失败告警                                                                                                    |
| 存储     | AppSecret 只存于密钥管理/环境变量，**不进代码仓库、不进客户端、不打日志**                                                                            |
| 传输     | 仅在服务端出网调用，客户端无任何微信侧密钥                                                                                                           |
| 权限前置 | 小店后台的「关联小程序/小游戏」授权**已完成**（2026-11-14 确认）；活动 `ACTIVITY_ID` 的礼物池包含 6 款玩偶商品（由活动侧配置，游戏侧不感知商品编号） |
| 日志脱敏 | openid 中间 4 位打码；`present_order_id` 可全量记录（便于排查）                                                                                      |

### 8.2 `animal_cfg`（动物与阈值配置）

```sql

  `animal_id`      VARCHAR(32)  NOT NULL COMMENT '动物唯一ID，不可改名',
```

### 8.3 `user_animal_fragment`（碎片进度）

```sql
CREATE TABLE `user_animal_fragment` (
  `id`              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `openid`          VARCHAR(64)  NOT NULL,
  `animal_id`       VARCHAR(32)  NOT NULL,
  `fragment_cnt`    INT          NOT NULL DEFAULT 0 COMMENT '当前可用碎片（兑换会扣减）',
  `total_obtained`  INT          NOT NULL DEFAULT 0 COMMENT '历史累计获得（只增不减，用于汇总展示）',
  `redeemed_cnt`    INT          NOT NULL DEFAULT 0 COMMENT '该动物成功兑换件数（冗余，便于快速校验L1）',
  `last_obtain_at`  DATETIME     NULL COMMENT '最近获得碎片时间',
  `version`         INT          NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
  `created_at`      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_openid_animal` (`openid`, `animal_id`),
  KEY `idx_openid_updated` (`openid`, `updated_at`)
) COMMENT='用户碎片进度（一个用户×一只动物=一行）';
```

约束：`fragment_cnt >= 0`、`total_obtained >= fragment_cnt + redeemed_cnt × threshold` 由应用层保证（DB 层不加 CHECK，避免线上改阈值时锁表）。

### 8.4 `fragment_log`（碎片流水，只追加）

```sql
CREATE TABLE `fragment_log` (

  `openid`      VARCHAR(64) NOT NULL,
  `animal_id`   VARCHAR(32) NOT NULL,
  `delta`       INT         NOT NULL COMMENT '正数=获得，负数=兑换扣减/回滚',
  `balance`     INT         NOT NULL COMMENT '本次变动后的 fragment_cnt',
  `reason`      VARCHAR(32) NOT NULL COMMENT 'round_finish / redeem / redeem_rollback / gift_expired / manual',
  `ref_id`      VARCHAR(64) NULL COMMENT '关联 round_id 或 exchange_no',
  `created_at`  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_openid_time` (`openid`, `created_at`),

```

> `uk_reason_ref` 是**关卡结算幂等的第二道保险**：同一 `round_id` 的 `round_finish` 只能写一条。

## 9. 关键流程说明

### 9.1 流程一：过关 → 发碎片

```
[1] 客户端完成第二关清盘
        ↓
[2] POST /api/v1/round/finish  { round_id, result: 'clear_all_win' }
        ↓
[3] 服务端查 round_id 是否已结算
        ├─ 已结算 → 直接返回首次结果（幂等，不再发碎片）
        └─ 未结算 ↓
[4] 校验：反作弊（时长/步数）、日碎片上限(60)、掉落开关
        ↓
[5] 加权随机命中 1 只动物（排除已兑满 3 件的动物）
        ↓
[6] UPSERT user_animal_fragment  +1 / +1
    INSERT fragment_log(+1, reason=round_finish, ref_id=round_id)
    UPDATE level_round SET result
        ↓
[7] 返回 gained_fragment{animal_id, fragment_cnt_after, threshold, unlocked}
        ↓
[8] 客户端胜利框播放碎片进度动画；unlocked=true 时显示"去兑换"
```

### 9.2 流程二：兑换 → 发礼物

```
[1] 家园卡片按钮 unlocked
        ↓
[2] 确认框 → 点"确认兑换"（生成 client_token）
        ↓
[3] POST /api/v1/gift/redeem { animal_id, client_token }
        ↓
[4] 事务A：校验 C1–C5 / L1–L5 → 扣碎片 → 建单(init)
        ↓
[5] create_present_order(activity_id=ACTIVITY_ID, openid, shop_appid=SHOP_APPID,
                          wishmessage, idempotent_id)
        ├─ 成功 → 事务C 回填 present_order_id, status=created
        │         → 返回 {present_order_id, fragment_after}
        │         → 客户端 wx.createStoreGift → isSupported → open()
        │         → 轮询 getOrderInfo
        │         → 收到 orderStatus=20 → POST /gift/status → 服务端 get_present 校准
        │         → status=received，吐司"兑换成功，可在兑换记录查看物流"
        ├─ 明确失败 → 事务D 回滚碎片 + status=failed → Toast 原因
        └─ 结果未知 → status=unknown，返回"处理中"，补偿任务收敛
```

### 9.3 流程三：状态回收（定时任务）

| 任务           | 频率       | 逻辑                                                                                                                                       |
| -------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `unknown` 收敛 | 30s        | 同 `idempotent_id` 重放建单，按 §6.7 处理                                                                                                  |
| 未终态订单刷新 | 每小时     | 扫描 `status ∈ {created, received, shipped}` 且 `created_at` 在 7 日内，调 `get_present` 更新状态；`expired/refunded/cancelled` 触发退碎片 |
| 过期兜底       | 每天 03:00 | 建单超 72h 仍 `created` 且 `getOrderInfo` 为 180/181 → 退碎片                                                                              |
| 门槛重算       | 每天 03:10 | 按 `fragment_log` 重算 `fragment_cnt` 与 `total_obtained`，与主表比对，不一致告警（不自动修，防放大错误）                                  |

### 10.1 埋点事件

| 事件               | 触发                      | 参数                                                  |
| ------------------ | ------------------------- | ----------------------------------------------------- |
| `home_click`       | 点击家园按钮              | `redeemable_cnt`                                      |

| `redeem_success`   | 建单成功                  | `animal_id`、`exchange_no`、`cost`、`ms`              |

### 10.2 核心指标

| 指标            | 定义                                     | 目标方向                          |
| --------------- | ---------------------------------------- | --------------------------------- |
| 碎片获取率      | 有过关用户中当次获得碎片的比例           | ≥ 99%（正常应恒为 1）             |
| 首只解锁天数    | 注册到达成任一动物阈值的自然日           | 观察值，用于校准 §3.5             |
| 解锁→点击转化   | `redeem_click(unlocked) / fragment_full` | ≥ 60%                             |
| 点击→建单成功率 | `redeem_success / redeem_submit`         | ≥ 98%                             |
| 建单→领取率     | `gift_receive / redeem_success`          | ≥ 85%（低于此说明蓝包体验有问题） |
| 已兑用户次留    | 兑换成功的用户次日留存 vs 大盘           | 应显著高                          |
| 退碎片率        | `expired+refunded+cancelled / created`   | ≤ 5%                              |

## 11. 边界与异常总表

| #   | 场景                                 | 处理                                                                    |
| --- | ------------------------------------ | ----------------------------------------------------------------------- |
| 1   | 同一 `round_id` 重复上报             | 返回首次结果，不重复发碎片                                              |
| 2   | 同一 `client_token` 重复提交         | 返回已有 `gift_order` 结果，不重复扣碎片                                |
| 3   | 弱网下用户连点兑换                   | 前端 loading + 后端唯一键，双保险                                       |
| 4   | 兑换建单中用户杀掉进程               | 订单停在 `init`，30s 后由补偿任务收敛；重新进入家园卡片显示"处理中"     |
| 5   | 用户在另一台设备同时兑换同一动物     | 条件更新 `WHERE fragment_cnt >= threshold`，仅一台成功，另一台返回 1004 |
| 6   | 阈值被运营中途上调                   | 卡片可能回落为 `locked`，碎片不减少；活动期内建议冻结阈值               |
| 7   | 阈值被下调                           | 立即生效，可能出现"瞬间可兑"，需提前评估预算                            |
| 8   | 商品被下架 / 移出礼物池              | 该卡片置 `暂不可兑换`，不影响其他动物；高优告警                         |
| 9   | 活动库存耗尽                         | 提示"已兑完"，同步关闭 `gift_enabled`                                   |
| 10  | 活动到期                             | C5 失败，全部按钮 `活动已结束`；碎片保留                                |
| 11  | 微信版本 < 8.0.60                    | `isSupported()=false`，走降级文案 + 兑换记录入口                        |
| 12  | 基础库 < 3.8.12                      | 同上，并在启动时记录 `gift_unsupported`                                 |
| 13  | 用户在一台设备兑换、另一台打开旧面板 | 面板请求带服务端最新值，旧面板点兑换返回 1004 并刷新                    |
| 14  | `present_order_id` 超出 JS 安全整数  | 全程字符串传输与存储                                                    |
| 15  | 礼物被用户忽略至过期                 | 到期后 `get_present` 返回 180，退碎片，卡片进度恢复                     |
| 16  | 用户主动取消礼物单                   | 退碎片，但计入当日/累计次数（防刷）                                     |
| 17  | 售后退款                             | 礼物状态 200 → `cancelled`，退碎片，人工复核                            |
| 18  | 服务端时区错乱导致"今日"判断错误     | 统一 `Asia/Shanghai`，DB 与容器均设 UTC+8                               |
| 19  | 碎片被篡改（本地缓存改数）           | 客户端缓存仅展示，所有判定用服务端值，篡改无效                          |
| 20  | 动物名称变更导致卡片错乱             | `animal_id` 不可改名，显示名与 ID 解耦（后台限制）                      |
